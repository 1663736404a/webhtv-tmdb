# 播放性能自动档判断依据与最佳参数方案

- 日期：2026-07-24
- 代码基线：`beta` / `0f10f50044` / `playback-optimization-item-93`
- Media3：`1.11.0-alpha01-fongmi`
- 适用内核：EXO、MPV、IJK
- 目标：把现有多个固定性能档位逐步收敛为一个有真实设备、资源和运行反馈依据的“自动”档位

## 一、二次审阅结论

当前“自动”档位尚未形成三个内核统一的自动控制器：

1. EXO 已经具备真实下载吞吐、媒体码率、缓冲趋势、重缓冲、掉帧、播放路径和预载状态机，方向基本正确；但真实系统内存、事件驱动的内存压力、热状态、真实轨道 codec、当前输出模式和通用 decoder 运行档案尚未进入完整决策。
2. MPV 目前只有输出模式具备真正的自动判断；缓存、回看缓存、HLS 初始选轨、重缓冲和预载仍主要使用“推荐”固定值。
3. IJK 自动场景主要通过 URL scheme 判断 RTSP、RTP、UDP、RTMP，普通 HLS 直播不会被识别为直播；更严重的是自动/稳定 realtime 会开启 `infbuf`，锁定 native 源码明确表明它会绕过 `max-buffer-size` 停读条件。
4. EXO 并非没有检测内存：它已经读取 `isLowRamDevice()` 和 Java heap 上限。但三个内核都没有建立“事件回调为主、低频快照为辅”的内存反馈闭环；`PlaybackActivity.onTrimMemory()` 目前只记录日志。
5. 当前最先要修复的不是继续微调固定档位，而是确定性正确性和资源安全问题：HLS 代理强制最高 variant、EXO 带宽 cap 写错字段、IJK 无限输入缓存、磁盘剩余空间算法、过度乐观的初始带宽，以及 VBR 码率低估。
6. 不存在适用于所有 Android TV、协议和媒体的“网上最佳固定参数”。官方默认值只能作为基线，论文提供的是控制原则，本文的具体阈值只能作为保守产品起始值，最终必须由真机遥测校准。

### 1.1 对上一版方案的逐项修正

| 上一版结论 | 二次审阅结果 | 本版处理 |
|---|---|---|
| 每 15～30 秒采样 PSS | 不适合作为生产控制核心 | `getProcessMemoryInfo()` 仅定位为诊断采样；控制以 `onTrimMemory/onLowMemory`、`getMyMemoryState()` 和低频 `MemoryInfo` 为主 |
| 收到 `TRIM_MEMORY_RUNNING_LOW` 后缩容 | API 34 起 running 三个等级不再通知 App | 保留兼容处理，但不能依赖；增加 `onLowMemory`、当前 trim level、系统 `lowMemory/threshold` |
| 流媒体统一 `prioritizeTime=false` | 对高码率单轨可能在不足 500ms 时先撞字节目标 | 普通多码率流默认字节优先；高码率单轨仅在更早硬保护存在时启用受控时间优先 |
| EXO/MPV 256MiB 可按大内存设备自动启用 | 没有足够官方依据，且 Media3 新全局 guard 约 200MB | 256MiB 降为真机验证后的例外；默认上限取需求、约 200MB guard 和设备预算的最小值 |
| `availMem≥2GiB` 可证明安全 | 绝对值跨设备缺乏依据 | 删除硬编码 2GiB 条件，改用 `availMem/threshold`、trim、当前进程余量和趋势 |
| 0.97 是 VOD 自动降速的官方安全值 | 0.97～1.03 是 Media3 直播追赶 live edge 的默认范围 | VOD 降速默认关闭或明确 opt-in；多码率优先交给 ABR 降轨 |
| 静态 MediaCodec/PerformancePoint 足以定能力 | 设备可能报告支持但运行时仍崩溃 | 新增按设备、decoder、格式和输出模式维度的运行能力档案与版本化黑名单 |
| 低延迟直播固定 3～8 秒 | LL-HLS 有清单声明的 `HOLD-BACK/PART-HOLD-BACK` | 优先服从清单和 segment/part 粒度，固定值仅作缺省回退 |
| 当前输出 1080p 就不应选 4K | 用户锁定、即将切显示模式、高质量下采样时可能合理 | 当前模式作为约束之一，不作为绝对禁令 |
| MPV 缓存值只能在下次播放生效 | 锁定源码会在 demux thread 更新相关 option | 可运行时扩缩；但缩容后 packet pool/RSS 不保证立即完全回落，必须观测确认 |

自动档应遵循以下原则：

- 保守起步，测得真实能力后再扩张。
- 降级快、升级慢；严重风险立即降级，升级必须经过稳定窗口和冷却期。
- 对 HLS/DASH 多码率资源优先让 Media3 原生 ABR 选轨；对 progressive/REMUX 单码率资源使用缓存、预载和恢复控制，不虚构 ABR。
- 缓存字节由平均需求、突发需求和目标秒数计算，再受 Java heap、系统内存、native 进程余量和内核 guard 共同上限约束。
- 回看缓存和预载默认关闭或最小化，只在用户行为、网络、内存、计费和电源状态都证明有收益时开启。
- 用户明确选择的字幕、LUT、插帧、精确 Seek、播放速度和 `mpv.conf` 优先级不应被自动档擅自覆盖。
- 每次自动决策必须记录输入、置信度、旧值、目标值、原因和抑制原因，保证可解释、可复现、可回滚。

## 二、哪些参数应该自动判断

### 2.1 必须自动判断

| 参数 | 必要输入 | 目标 |
|---|---|---|
| 前向缓存字节 | 平均/峰值媒体码率、目标秒数、Java heap、系统压力、native 余量 | 避免固定 64/128/256MiB 一刀切 |
| 前向缓存秒数 | 本地/远程、VOD/live、Range、segment/part 时长、吞吐波动 | 平衡起播、稳定性、直播延迟和内存 |
| 起播与重缓冲阈值 | 首次吞吐、缓冲趋势、重缓冲历史、live offset、segment 边界 | 稳定资源快速起播，波动资源避免反复缓冲 |
| 多码率选择边界 | 可信吞吐、选中轨码率、buffer occupancy、预测误差 | 让 ABR 在可持续码率内选轨并减少震荡 |
| 分辨率、帧率和 codec 上限 | 真实轨道、当前 decoder 运行档案、显示模式、用户质量约束 | 不因理论能力选择无法稳定解码的轨道 |
| 硬解/软解/内核回退 | 首帧、codec 错误、持续掉帧、热状态、输出模式 | 优先硬解，失败后按已验证路径回退 |
| EXO 帧调度实验值 | 帧提前/延后分布、掉帧、设备型号、Perfetto | 只在证据证明有收益时调整 50ms 默认值 |
| MPV 输出模式 | TV/手机、硬解、字幕、LUT/滤镜、GPU 处理、失败历史 | 合适资源直出，其余 GPU 完整渲染 |
| 预载开关、线程和时长 | 前台缓冲、吞吐比、路径、内存、计费、漫游、电源和热状态 | 前台优先，0～2 线程动态变化 |
| 回看缓存 | 向后 Seek 频率、内存余量、资源可 Seek 能力 | 默认 0，真实行为证明需要后再开启 |
| live/VOD/LL-live 场景 | HLS/DASH 清单、RTSP、`ENDLIST`、target/part duration、hold-back | 不再仅依赖 URL scheme |
| RTSP live lag 恢复 | 当前延迟、数据增长、播放位置、重连历史 | 落后过多时跳到 live edge 或重建会话 |
| probe 和 RTSP transport | 容器、协议、首次探测结果、失败原因 | 已知格式快速探测，失败后升级或换传输 |
| 内存、热和电源降级 | trim、lowMemory、threshold、native 指标、thermal、battery saver | 压力出现时立即停止非必要工作 |
| 磁盘缓存容量 | 可用空间、保留空间、写入错误、缓存命中率 | 防止固定大缓存导致 ENOSPC |

### 2.2 可以自动提供默认值，但必须允许用户覆盖

- 音频直通：按电视/功放能力和格式自动启用，失败后回退 PCM。
- AAC 优先：只作为音频兼容性回退，不成为所有设备固定偏好。
- 帧率匹配：自动档可默认“仅无缝”，非无缝黑屏切换尊重用户选择。
- frame drop：使用播放器官方安全默认，检测持续解码过载后再增强。
- RTSP TCP/UDP：TCP 作为稳定默认，明确低延迟需要或 TCP 失败时再尝试 UDP。
- 软件解码降负载：只在真实软解、掉帧或热压力出现时启用。
- VOD 网络保护降速：默认关闭；若保留功能，必须由用户显式允许且只作为单码率资源最后救援。

### 2.3 不应被自动档主动覆盖

- 字幕选择、字幕渲染需求。
- LUT、画面滤镜、插帧等用户视觉偏好。
- 用户设置的播放速度。
- 精确 Seek 偏好。
- `mpv.conf` 与播放性能配置的优先级。
- 用户明确锁定的清晰度或“原版”质量选择。

自动控制器应把这些偏好作为约束条件参与判断。用户锁定原版时可以提示资源风险，但不能悄悄降档。

## 三、当前实现审计

| 应自动判断的项目 | 当前 EXO | 当前 MPV | 当前 IJK | 完备度 |
|---|---|---|---|---|
| 内存容量 | `isLowRamDevice + Runtime.maxMemory` | 固定缓存档位 | 固定 4/8/15MiB | EXO 部分完备，MPV/IJK 缺失 |
| 系统真实可用内存 | 未读取 | 未读取 | 未读取 | 缺失 |
| 内存压力回调 | `onTrimMemory()` 仅日志 | 无动作 | 无动作 | 缺失 |
| native/PSS | 未读取 | 未读取 | 未读取 | 只能补充为诊断，不应高频控制 |
| 热/省电/计费网络 | 未读取 | 未读取 | 未读取 | 缺失 |
| 真实吞吐 | Media3 BandwidthMeter | 已采集但未驱动配置 | 未形成闭环 | EXO 较好 |
| 缓冲趋势 | 快慢斜率、time-to-reserve | 已采集但未决策 | 仅事件/百分比 | EXO 较好 |
| 重缓冲学习 | 2～15 秒，按网络/路径/协议/资源类型隔离，14 天过期 | 固定 2 秒 | 固定水位 | EXO 已隔离持久先验，MPV/IJK 缺失 |
| 多码率选择 | Media3 ABR 加自定义只降控制器 | HLS 固定初始选轨 | HLS 固定初始选轨 | 职责需重构 |
| 播放路径 | 直连、App 服务、外部 loopback | 有网络恢复边界 | 通过同一 HLS 代理 | 部分完备 |
| 预载 | 0～2 线程状态机 | 固定 1 线程，主要 Seek 后 | 固定 1 线程 | EXO 较成熟 |
| 输出模式 | Surface/Texture、显示模式、tunneling | Surface Direct/GPU 自动切换 | 固定 Surface | MPV 较成熟 |
| codec 能力 | 固定 HEVC 预检 | 硬解失败回退 | 固定开关 | 没有通用运行能力档案 |
| live/VOD | 协议源可识别，策略未完整分层 | HLS 代理可识别 `ENDLIST` | scheme 判断 realtime | IJK 明显不足 |
| 磁盘空间保护 | 错把卷容量 80% 当预算 | 固定限额 | 与 MPV 共用代理 | 存在正确性问题 |

### 3.1 自动档入口没有统一为自动控制器

`PlaybackPerformanceSetting.applyAuto()` 中：

- EXO 调用 `ExoPerformanceSetting.applyAuto()`。
- MPV 调用 `MpvPerformanceSetting.applyRecommended()`。
- IJK 调用 `IjkPerformanceSetting.applyRecommended()`。

因此 MPV/IJK 自动档目前与推荐档基本相同，只是 MPV 输出模式内部另有自动状态机。三个内核可以共享事实层和状态分级，但不能把语义不同的缓存参数硬映射成同一数值。

### 3.2 EXO 内存预算存在，但反馈闭环不完整

`ExoBufferBudget` 当前读取 `isLowRamDevice()`、Java heap 上限、`memoryClass/largeMemoryClass` 和 `largeHeap` 标记；实际预算只使用前两者：

- low-RAM：Java heap 的 20%，预留 48MiB。
- 普通设备：Java heap 的 30%，预留 64MiB。
- 最低 16MiB，最高 256MiB。

| Java heap | 当前自动目标字节 |
|---:|---:|
| low-RAM 128MiB | 25.6MiB |
| low-RAM 192MiB | 38.4MiB |
| 普通 256MiB | 76.8MiB |
| 普通 384MiB | 115.2MiB |
| 普通 512MiB | 153.6MiB |
| 普通 1GiB | 256MiB 封顶 |

不足之处：

- `memoryClass/largeMemoryClass/largeHeap` 只进入诊断对象，不改变预算。
- 未读取 `MemoryInfo.totalMem/availMem/lowMemory/threshold` 和 `getMyMemoryState().lastTrimLevel`。
- `onTrimMemory()` 只记录日志，没有通知播放器停止预载、关闭 back buffer 或抑制扩张。
- MPV/IJK packet cache 主要属于 native 内存，只看 Java heap 无法决定安全值。
- `getProcessMemoryInfo()` 官方明确只用于调试或用户可见进程管理 UI，Android Q 起还会限频；不能按 15～30 秒持续轮询作为生产控制核心。PSS 只适合起播前后、错误快照、人工诊断或稀疏遥测。
- Android 14/API 34 起 `TRIM_MEMORY_RUNNING_MODERATE/LOW/CRITICAL` 不再通知 App，不能把这些回调写成唯一触发器。

正确模型是：`onTrimMemory/onLowMemory` 事件为主，`getMyMemoryState()` 恢复当前状态，`MemoryInfo` 在会话边界或低频校验；Java/native/PSS 仅补充诊断与趋势证据。

### 3.3 EXO target bytes 是软预算，时间优先也不能全局化

自动档通过 `ExoLoadControlPolicy.prioritizeTime()` 强制时间优先。Media3 在未达到最小时间时，即使 target bytes 已达到也可能继续加载，因此 `ExoBufferBudget` 不是严格硬上限。

但简单改成全局 `false` 同样不完整：Media3 issue #2298 展示了 target bytes 已达到而缓冲不足 500ms 的高码率案例，维护者建议按媒体配置 LoadControl，或受控启用 `setPrioritizeTimeOverSizeThresholds(true)`。另一方面 issue #2860 又推动了约 200MB 的全局 guard，说明时间目标不能无限突破内存安全。

建议分支：

- HLS/DASH 多码率：默认字节优先，内存受控，并优先降轨。
- progressive/REMUX 高码率单轨：当已确认当前字节预算不足以维持最小可播时间，且 Java/system memory 硬保护已启用时，可受控时间优先。
- 一旦 trim、`lowMemory`、headroom 不足或 guard 告警，无条件以资源安全为先。
- 目标字节应取 `min(媒体需求，约 200MB Media3 guard，设备会话预算)`；项目现有 256MiB 只能是经过专项验证的例外。

### 3.4 初始网络估计过度乐观，链路带宽也不等于吞吐

当前实现：

```text
Wi-Fi/Ethernet = max(设备目标码率 × 2, 20Mbps)
5G             = max(设备目标码率 × 1.5, 15Mbps)
4G             = max(设备目标码率, 8Mbps)
```

4K 能力设备在 Wi-Fi/Ethernet 上会直接以 40Mbps 作为初始估计。Media3 当前依赖版本内置初值按国家/网络分组通常只有约 0.68～4.7Mbps。当前值可能高 5～10 倍，容易在首个真实样本出现前选择过高轨道。

- 首次选轨恢复 Media3 内置先验，或仅使用经过实测的保守产品先验。
- `NetworkCapabilities.getLinkDownstreamBandwidthKbps()` 只能作为接入链路先验，不能代表 CDN、网盘、VPN、代理或服务端限速后的真实吞吐。
- 当前 `setSlidingWindowMaxWeight(4000)` 比默认 2000 更平滑，但弱网恶化时更迟钝。自动档应同时维护短期风险窗口和长期稳定窗口。
- 外部 loopback 的本地腿吞吐绝不能用于上游升档或开启预载。

### 3.5 自定义 EXO 降档控制器与 Media3 ABR 职责重叠且存在字段错误

`AdaptiveVideoProfileController` 当前有四个问题：

1. `capByBandwidth()` 修改 `EnhancedVideoProfile.bitrate`，但 TrackSelector 实际使用 `maxVideoBitrate`，计算出的安全码率没有写入约束。
2. 比较的是 profile 名义码率，不是实际选中 Format 的码率。
3. 控制器只降不升，与 Media3 `AdaptiveTrackSelection` 的实时 variant 选择重叠。
4. `setExceedVideoConstraintsIfNecessary(true)` 允许必要时超过约束，因此 cap 不是绝对保证；必须回读实际选中 Format 验证。

职责应改为：

- HLS/DASH 多码率：Media3 ABR 负责实时选轨；自定义层只提供设备、显示、codec、计费和故障黑名单上限。
- progressive 单轨：没有可降 variant，码率 cap 无意义；使用缓存、预载、恢复或向用户报告不可持续。
- 重缓冲或 codec 故障时，自定义层可以降设备 profile/分辨率上限，但不能同时维护另一套持续 ABR。

### 3.6 codec 静态能力不能作为唯一事实

当前 `detectPlaybackCapability()` 固定以 HEVC 和设备最大显示模式预检；实际资源可能是 H.264、AV1、VP9、Dolby Vision 或不同 profile/level。Media3 issue #379 还记录了 TCL/Realtek 设备静态返回 `format_supported=YES`，运行时仍发生 MediaCodec 错误。

自动档应维护运行能力档案，键至少包含：

```text
Build fingerprint + App/Media3 版本 + decoder 名称 + MIME + profile/level
+ 分辨率/帧率 + secure + output mode/tunneling
```

记录首帧成功、稳定播放时长、codec error、掉帧率和回退结果；失败后建立有版本失效条件的黑名单。当前 tunneling failure memory 不能替代通用 decoder 能力档案。

当前输出模式是重要输入，但不是绝对上限：若即将切换输出模式、用户锁定原版或明确需要高质量下采样，1080p 输出仍可能合理选择 4K 源。

### 3.7 媒体码率估计会低估 VBR/REMUX 突发需求

`ObservedMediaBitrateEstimator` 只要 `Format.bitrate > 0` 就直接返回 format 值，忽略已经观测到的 p50/p90 和内容平均码率。对 VBR、REMUX 或封装中不准确的 bitrate，这可能低估缓存字节需求。

建议区分：

- 平均需求：format bitrate、文件长度/时长、HLS `AVERAGE-BANDWIDTH`。
- 峰值/突发需求：可信 observed p90、HLS 必填的 `BANDWIDTH`、近期 segment 实际大小/时长。
- 缓存预算使用 `max(可信平均值，可信 observed p90)`，再受内存 guard 限制；低置信度观测只允许保守抑制升级，不能立即扩张大内存。

`PlaybackBytePositionDataSource` 使用全局静态 `sequence/positionBytes`，每个 DataSource `open()` 都会递增 sequence。HLS/DASH 音视频、清单、分片并发打开会互相打断窗口，因此 byte-position slope 只适合确认过的单连续 progressive 流，不能泛化到所有协议。

### 3.8 MPV 缓存固定偏大，但运行时扩缩是可行的

自动/推荐档当前约为：

- forward：256MiB。
- back：约 128MiB。
- `cache-secs=30`、`demuxer-readahead-secs=30`。
- 重缓冲等待：2 秒。
- HLS：最高码率。
- 预载：1 线程、20 秒。
- HLS 代理磁盘缓存：通常 512MiB。

锁定 mpv 源码确认：demux thread 会调用 `m_config_cache_update()` 更新 `demuxer-max-bytes/back-bytes`；总上限缩小时还会清 packet pool。因此动态扩缩可实现，但 RSS/PSS 不保证同步、完整下降，必须继续观测 `fw-bytes/total-bytes/PSS`。

其他语义边界：

- back 默认可借用未使用的 forward，总占用仍可接近 forward + back。
- cache 启用时 `cache-secs` 会覆盖或取大于 `demuxer-readahead-secs`，当前两者都设 30 秒语义重复。
- `demuxer-hysteresis-secs/bytes` 可让读取成块发生，减少持续网络/磁盘工作和功耗；可从很小值实验，不能在波动 loopback 上盲目加大。
- `hls-bitrate` 只控制初始固定选轨，运行时改值不会自动无缝 ABR；降级需要明确的重载/重启方案。

### 3.9 HLS 代理破坏 MPV/IJK 选轨

`MpvHlsProxy.lowerVariantLinesToSkip()` 删除 master playlist 中除最高码率/分辨率外的所有 variant。后果是 MPV 的 8/15Mbps/min 设置可能无效，IJK 也只能看到最高档。

代理应保留完整 master playlist，或按内核明确要求选择一个 variant，但不能无条件删除低档。RFC 8216 语义上：

- `BANDWIDTH` 是所有可播放 rendition 组合的峰值上界，且必填。
- `AVERAGE-BANDWIDTH` 是平均 segment bitrate，可选。

当前代理 `variantBandwidth()` 优先平均值用于“最高档”排序，不适合作为安全峰值判断；自动预算应同时保留两个字段。

### 3.10 IJK `infbuf` 是高优先级内存风险

当前只有 `rtsp/rtp/udp/rtmp` 被认为 realtime，普通 HTTP HLS live 不进入直播场景。对 realtime，自动/直播稳定场景会设置 `infbuf=1`。

锁定 IJK native 源码的停读条件是：只有 `infinite_buffer < 1` 时才检查三路 packet queue 是否超过 `dcc.max_buffer_size`。所以 `infbuf=1` 不是“更稳定地使用 15MiB”，而是直接绕过 15MiB 的输入队列停止条件，长时间直播或消费速度不足时可持续增长内存。

- 自动档默认必须关闭 `infbuf`，除非另有真正的硬上限和长时压力测试证明安全。
- 直播稳定性应通过水位、延迟恢复、丢包/重连和有限 buffer 控制，不能用无限队列替代。
- HLS/DASH live 识别应基于清单；RTSP/RTMP 才可结合 scheme 和协议元数据。

### 3.11 RTSP 不能只调缓存

Media3 issue #845 指出 `RtspMediaSource` timeline 的 `isDynamic=false` 会使 `LivePlaybackSpeedControl` 不生效；弱网后播放位置可能长期落后 live edge，并伴随内存增长。因此 RTSP 需要单独策略：

- 计算或近似 live lag，而不是只看 forward buffer。
- 超过最大允许延迟后跳到最新位置、丢弃旧数据或重建会话。
- 监听长期内存增长并设置会话恢复边界。
- HLS/DASH 可以依赖 timeline/manifest live 配置，不能把同一处理假定适用于 RTSP。

E-10 已按这一边界接入 EXO 自动档：只有 F-02 明确分类为 RTSP、资源分类与播放器回调共同确认 live、已完成起播且仍有播放意图的会话才采样。当前以 30 秒 live lag 为保守上限；15 秒以上且每秒继续增长至少 500ms 也视为落后风险。普通风险要求至少 3 个样本和 10 秒持续确认，120 秒以上的紧急风险仍要求 2 个样本和 5 秒确认。`getCurrentLiveOffset()` 不可用时不猜 live edge，只在 `getTotalBufferedDuration()` 已达到 90 秒且每秒继续增长至少 500ms 时，把它作为异常队列增长代理并仅允许重建会话；该代理不是 native RSS 或服务端绝对时间的替代。

跳最新位置还要求 `Timeline.Window.isLive=true`、`isDynamic=true`、live offset 可用且 `COMMAND_SEEK_TO_DEFAULT_POSITION` 可用；否则直接重建 RTSP media session，不向未知位置 Seek。每会话最多尝试 1 次 live-edge Seek、2 次会话重建、总计 3 次；Seek 冷却 30 秒，重建冷却 90 秒。暂停、用户 Seek、位置不连续、错误、资源替换和旧 SessionToken 都会清除旧观察，动作次数在调用 Media3 前提交，避免同步回调重复触发。该策略不能证明服务端 live edge 正确，也不能用单测替代真实 RTSP 长时内存和弱网验证。

### 3.12 EXO 帧调度已有实验 API，不能盲目改常量

当前依赖已经包含：

- `setVideoRendererEarlySchedulingThresholdUs()`，默认 50ms。
- `setEnableMediaCodecVideoRendererDurationToProgressUs()`。

Media3 issue #2990 和 2026-07 提交 `bce59af...` 表明维护者认可某些 TV 需要不同提前调度值，但默认仍在研究。建议对问题设备做 50/75/100ms 受控 A/B，使用现有 frame timing、掉帧和 Perfetto 证据；不能仅按“电视设备”全局放大。启用 duration-to-progress 后会改变 offset 观测分布，诊断阈值也必须同步校准。

### 3.13 磁盘缓存没有真正保留可用空间

EXO 当前：

```text
storageBudget = (cacheUsed + available) × 80%
capacity = min(configured, storageBudget)
```

这近似按卷总容量预算，不是“保留 20% 当前可用空间”。当磁盘只剩很少空间时，仍可能允许配置的 512MiB 缓存。`MpvHlsProxy` 只按 play/preload 固定限额 prune，也没有剩余空间 guard。

建议公式：

```text
reserve = max(卷容量 × 10%, 512MiB)
newWriteBudget = max(0, availableBytes - reserve)
capacity = min(configuredCapacity, existingCacheBytes + newWriteBudget)
```

10%/512MiB 只是保守产品起点，不是平台官方最佳值。每次大文件写入前和写入过程中都要复核空间；收到 ENOSPC/写失败后立即取消预载、停止新缓存并 prune。EXO `SimpleCache` 容量只能在活动 session 释放并重建后生效，文档和 UI 要明确生效时机。MPV native packet cache 与 HLS 代理磁盘缓存是两层预算，不能把两者混为一个“缓存”。

## 四、可信基准与研究结论

网上参数应按证据等级使用：

1. 当前依赖源码和官方协议：可作为语义与默认基线。
2. 维护者 Issues/提交：可证明真实边界和演进方向，但未关闭 issue 不能当已解决事实。
3. 论文和成熟项目：用于控制原则、对照和实验设计，不能把实验阈值直接套到 Android 单码率 REMUX。
4. 博文/论坛经验值：只能生成待验证假设，不能直接进入自动默认。

### 4.1 Media3 DefaultLoadControl

当前依赖的常量：

| 参数 | 流媒体 | 本地播放 |
|---|---:|---:|
| min buffer | 50 秒 | 1 秒 |
| max buffer | 50 秒 | 50 秒 |
| 起播 | 1 秒 | 1 秒 |
| 重缓冲恢复 | 2 秒 | 1 秒 |
| prioritize time | false | true |
| back buffer | 0 | 0 |

字节基准：muxed 约 144,310,272 bytes，全轨道最大约 210,239,488 bytes，segment 为 64KiB。Media3 issue #2860 的维护者建议约 200MB 作为全局 guard，约为 muxed 默认上限的 1.5 倍；这支持项目把 256MiB 从默认候选降为实验例外。

E-02 已在自动档接入 Media3 正式的 streaming/local 独立构造语义：流媒体使用 30/60 秒 min/max、自动会话起播值、15 秒最大重缓冲阈值和字节优先；本地使用 1/15 秒 min/max、500ms 起播、1 秒重缓冲和时间优先。非自动档继续使用原通用配置，不改变用户既有设置。

### 4.2 Media3 AdaptiveTrackSelection 和直播速度

当前版本 ABR 默认：bandwidth fraction 0.7，升档前最小缓冲 10 秒，降档参考 25 秒，丢弃低清片段后至少保留 25 秒，live edge 升档比例 0.75。

这些值应优先交给 Media3 原生 ABR，而不是再造一套每次 bandwidth callback 都降 profile 的算法。0.7 是官方算法的输入之一，不等于任何协议下都强制“码率≤0.7×单次吞吐”。外部 loopback 或预测误差大时只能降低置信度、限制升级。

`DefaultLivePlaybackSpeedControl` 默认 0.97～1.03、每 1 秒调整、rebuffer 后 target live offset 增加 500ms。这是直播延迟控制，不是 VOD 弱网保护的标准依据。

### 4.3 MPV 精确版本语义

bundled mpv `0.41.0-878-g94335ab87` 默认：

- `demuxer-max-bytes=150MiB`。
- `demuxer-max-back-bytes=50MiB`，默认允许 back 借用 forward。
- `demuxer-readahead-secs=1`。
- `cache-secs` 默认极大，通常由 bytes 限制。
- `cache-pause-wait=1`。
- `demuxer-hysteresis-*=0`，官方文档称 10 秒可能适合很多通用场景，但项目只能从小值 A/B。
- `framedrop=vo` 是推荐默认。
- `hls-bitrate=max` 是固定初始选择，不是动态 ABR。

MPV 默认面向多平台，不能直接作为 Android 最佳值；但当前统一 256+128MiB 明显高于原生默认，必须由设备预算和真实需求解释。

### 4.4 IJK 锁定版本语义

- max queue：15MiB。
- first/next/last water：100/1000/5000ms。
- picture queue：3。
- packet buffering：开。
- `infbuf`：明确表示不限制 input buffer，并绕过 max queue 停读分支。

因此 4/8/15MiB 可作为有限缓存实验层级，但任何层级都不能与 `infbuf=1` 同时被宣称为硬上限。

### 4.5 HLS/LL-HLS 协议依据

- RFC 8216 要求客户端普通 live 起播不要靠 live edge 小于 3 个 target duration，过近会增加 stall 风险。
- HLS 2nd Edition 草案使用 `HOLD-BACK` 和 `PART-HOLD-BACK` 表达服务端建议的 live 距离；缺省 hold-back 为 3×target duration，part hold-back 通常至少 3×最大 part target。
- 短 target/part 能降低延迟，但同时减少可用缓冲、削弱 ABR 并增加开销和 stall 风险。
- hls.js 也把 live sync 默认表示为 3×target duration，LL-HLS 优先从 `PART-HOLD-BACK` 起播；它还在延迟过大时 seek 回 live sync point，而不是无限缓存旧数据。

自动档应按 segment/part 边界设置阈值；“3～8 秒”只能在清单缺失相关声明时作为兜底范围。

### 4.6 ABR 论文可吸收的原则

- BBA/BOLA：buffer occupancy 本身是重要控制变量，弱化对瞬时吞吐预测的依赖。
- MPC/robustMPC：使用近期吞吐的调和均值，并显式按历史预测误差下修未来吞吐；证明单个平滑窗口不够。
- FESTIVE：质量稳定性和 hysteresis 是 QoE 的组成部分，不能网络一恢复就频繁升降。
- Pensieve：QoE 奖励同时惩罚重缓冲和质量切换，说明“最高画质”不是唯一目标。
- Puffer：真实部署会暴露预测误差和训练/部署分布差异，不能把离线或单一网络 trace 的 ML 参数直接发布为默认。

这些原则只适用于存在多个可切 variant 的 ABR 场景。单码率网盘 REMUX 没有可选动作空间，主要问题是可持续吞吐、缓存和资源恢复。

### 4.7 成熟项目对照

- Jellyfin Android TV 的 `AUTO` 使用 Media3 默认 buffer；50～120 秒和 80～240 秒作为用户显式选择的“大/超大”档，而非自动默认。
- Kodi 当前网络文件缓存默认约 64MB，读取倍率默认 adaptive。
- hls.js 默认同时使用约 30 秒和 60MB 两类限制，并明确时间目标可能优先于字节目标、另有 600 秒绝对时间上限。

这些项目的运行环境不同，数值不能照搬；共同点是默认保守、协议感知、用户大缓存显式化，而不是把最大缓存称为自动最优。

## 五、自动决策输入与可信度

### 5.1 设备与系统层

持续维护：

- `isLowRamDevice()`、Java heap limit/current used/headroom。
- `MemoryInfo.totalMem/availMem/lowMemory/threshold` 的会话边界与低频快照。
- `onTrimMemory/onLowMemory` 事件和 `getMyMemoryState().lastTrimLevel`。
- `Debug.getNativeHeapAllocatedSize()` 等低成本进程指标；PSS 仅诊断或极稀疏遥测。
- thermal status/listener、Battery Saver。
- 当前和支持的显示模式、电视/功放音频能力。
- 实际 decoder 运行档案，而不只静态 `MediaCodecList/PerformancePoint`。
- 可用磁盘、卷容量和缓存已用空间。

### 5.2 网络、资源与路径层

- 本地、LAN、远程 HTTP、App 服务、外部 loopback、VPN。
- unmetered/metered、roaming、Data Saver、validated、Battery Saver。
- progressive Range、HLS、DASH、RTSP、RTMP。
- VOD、普通 live、LL-live；HLS target/part duration、hold-back、`ENDLIST`；DASH static/dynamic。
- 当前实际选中轨的 MIME/profile/level、分辨率、帧率、HDR、平均/峰值码率。
- 单码率还是多 variant；是否支持 Range/Seek，长度和时长是否可信。
- 代理能否暴露真实上游吞吐；无法暴露时降低所有吞吐驱动升级的置信度。

### 5.3 实时反馈层

- 短/长窗口吞吐分布和预测误差，不能只用一个瞬时或平滑值。
- 平均/峰值媒体码率、当前选中 Format、吞吐/需求比。
- forward buffer、变化斜率、time-to-empty、live lag。
- loading/idle、underrun、paused-for-cache、重缓冲次数和时长。
- 掉帧、渲染提前/延后、decoder error、实际 hwdec/VO/output。
- trim/lowMemory、Java/native 增长、thermal 和电源状态。
- 向前/向后 Seek、质量锁定、用户主动回退。

### 5.4 每个输入必须带置信度

| 输入 | 高置信度 | 降低置信度的情况 |
|---|---|---|
| 吞吐 | 真实上游、多个完整 segment/Range 样本 | 首次样本、loopback 本地腿、VPN、并发预载 |
| 媒体平均码率 | 可信清单/Format 与内容长度一致 | 封装错误、VBR、未知 duration |
| 媒体峰值 | HLS `BANDWIDTH`、多个 segment p90 | 只有文件平均值或单个异常样本 |
| codec 能力 | 同 fingerprint/decoder/格式长期成功 | 仅静态 API 报告、系统或 App 刚升级 |
| 内存余量 | trim/lowMemory 事件、heap headroom | 单次 `availMem` 或陈旧 PSS |
| live edge | manifest/timeline 明确 | RTSP 无可靠 timeline、服务端时间未知 |

低置信度输入可以阻止升级或触发保守模式，但不应单独驱动大幅扩容、升清晰度或持久黑名单。

当前实现进度：F-01 已建立进程级不可变 `PlaybackAutoContext` 快照和会话隔离发布器，统一携带来源、置信度、单调采样时间与过期规则；F-02 已接入保守的协议、资源与双腿路径分类，覆盖本地/LAN/远程/内部服务/外部 loopback、Progressive/HLS/DASH/RTSP/RTMP、VOD/live/LL-live、Range 和 segment/part，并从 EXO DataSource 与 MPV/IJK 共享代理补充实际响应和清单证据；F-03 已接入 Java heap、`MemoryInfo`、`getMyMemoryState()`、low-RAM、native heap、稀疏 PSS 以及 `onTrimMemory/onLowMemory` 事件，使用 Application 唯一入口、会话隔离协调器、约 30 秒低频刷新和至少 5 分钟 PSS 间隔分发带 TTL 的内存事实，API 34+ 不依赖废止的 running trim；F-04 已接入 active/validated/metered/roaming、transport、Data Saver、Battery Saver 和 API 29+ thermal status，在活动会话内监听变化并以约 60 秒刷新、120 秒 TTL 发布脱敏事实，VPN、权限/API 缺失和旧系统 thermal 均保守降置信度或保持 UNKNOWN；F-05 已接入实际音视频 MIME/codecs/profile/level、分辨率、帧率、HDR/色彩、平均/峰值码率、decoder 名称与软硬解、MPV 实际 `hwdec-current/current-vo`、Surface/Texture 和当前/目标显示模式，并以会话 token 与轨道序列隔离轨道切换期间的迟到 decoder；F-06 已接入进程级结构化决策事件、约 5 秒运行采样、15/30 秒 TTL、10 秒决策去重、15 秒运行日志限频和 bounded session summary，统一覆盖 network protection、MPV output、display request、preload/cache，并记录来源、置信度、首帧、buffer、吞吐、媒体码率、显示帧率、掉帧、重缓冲、内存条件和可用 live lag。EXO 只接受当前 trace 的实际输入格式和 decoder，自适应组选中多个候选时保持未知；MPV 属性失效后不沿用旧值；IJK 用 native stream index 对齐实际轨道。UNKNOWN 不猜测，外部 loopback 后方保持 opaque，live 清单及系统状态按真实观察时间过期。F-06 遥测只写本地调试日志，不建立远程上传，也不改变任何自动播放策略。

E-01 已将 EXO 自动档从固定 target bytes 改为轨道选择边界上的需求/容量双向分层：平均需求按 30 秒和 1.15 余量计算，突发需求按可信 peak/observed p90 的 10 秒窗口计算，优先采用 P0-08 的中高置信度估算，缺失时退回实际选中音视频 Format；需求向上取 16/24/48/64/96/128/192MiB 层级，安全容量按约 200MB guard、用户明确上限、原有 heap 比例预算、未过期 Java headroom 减 48/64MiB reserve、`systemAvailable-threshold` 的最小值向下取层。critical pressure、`lowMemory=true` 或系统余量到阈值时只允许最低 16MiB，过期/UNKNOWN 内存事实不按 0 使用，PSS 仍仅用于诊断。实际 target 通过会话隔离协调器同步给预载安全水位、轨道诊断和 F-06 `load-control` 决策日志；非自动档保持原固定行为。E-01 交付时 target 仍处于全局时间优先的软目标语义，该限制已由 E-02 收窄；自适应组内切轨后的持续重算已由 E-05 补齐，压力事件即时缩容与迟滞恢复已由 E-03 补齐，本项没有完成真机高码率或 OOM 验证。

E-02 已按资源类型分离自动档 LoadControl。实际自适应视频选择或 HLS Master 明确存在多个 Variant 时使用字节优先；单 Variant HLS/DASH 仍保持字节优先，避免 segmented 资源因时间优先绕过 target。Progressive 非自适应高码率视频仅在控制码率至少 50Mbps、当前 target 不足 3 秒、当前 Java/system 内存事实可用且压力为 NORMAL、3 秒所需字节不越过 192MiB guard/用户上限/设备预算时，临时允许受控时间补足至 3 秒；每次加载判断继续复核最新内存事实、allocator 硬容量和 Media3 的 4% heap headroom guard，任何保护拒绝后立即退回字节优先起播，避免等待与加载互锁。UNKNOWN、过期事实和 MODERATE/CRITICAL 压力不能启用该例外。模式按 `PlayerId` 和播放会话隔离，新增诊断不记录 URL、路径或异常正文；持续轨道需求重算已由 E-05 补齐，动态起播/重缓冲和趋势门槛已由 E-06 接入，压力迟滞恢复已由 E-03 接入。

E-03 已把 F-03 内存事实接入 EXO 自动控制器的运行期闭环。进程级协调器按当前 EXO 会话保存不受瞬时压力覆盖的媒体需求 baseline，并向 LoadControl、Media3 preload 和自定义 `PreCache` 分发 effective target；因此首次选轨恰逢 critical 时只会临时使用 16MiB，不会把恢复上限永久钉死。CRITICAL 立即回最低层，MODERATE 只降一档且不重复棘轮，当前 Java/system 安全容量下降立即收紧；降级期 back buffer 为 0、禁止 retain、暂停两类预载、禁用 Progressive 3 秒补足，并按前台 `PlayerId` 阻止越过有效层级的新 allocation，同时下调 allocator target 和 trim 空闲 allocation。恢复要求可用快照、两个新鲜 NORMAL 样本、30 秒稳定窗口；CRITICAL 冷却 60 秒，MODERATE/容量下降冷却 30 秒，此后每个新鲜样本最多恢复一档且不越过当前 safe ceiling。UNKNOWN、过期、重复或乱序样本不能扩容，完全恢复后预载仍需重新通过前台安全水位。新增日志仅记录枚举、容量、计数和动作；allocator 已引用数据不会被承诺即时释放，当前也没有真机 OOM/LMK 或系统杀进程端到端结论。

E-04 已拆开项目安全限制层与 Media3 ABR 的职责。EXO 自动档不再根据项目带宽回调或重缓冲事件修改 TrackSelector，HLS/DASH 多 Variant 的实时升降档由锁定版本 Media3 ABR 独立完成，Progressive 和单 Variant 分段资源也不再执行虚假的 variant 降级；非自动档仍保留原控制器。项目层只保留由设备最大显示能力、静态 codec 能力形成的 baseline，以及实际软解、thermal severe/critical、远程 metered、roaming、Data Saver、掉帧和 codec error 形成的安全上限：实际软解最高 1080p30/6Mbps，severe 最高 1080p30/8Mbps，critical、roaming 或 Data Saver 最高 720p30/4Mbps，远程 metered 最高 1080p60/8Mbps，本地/LAN 不受计费上限影响。thermal moderate 与 Battery Saver 只阻止恢复；故障每 15 秒最多降一层，至少保持 30 秒，再经 30 秒稳定窗口放宽，并要求恢复证据在整个窗口持续有效。UNKNOWN、过期事实、旧 trace/session 均不能解除约束，新会话恢复 baseline，release 时解绑监听和定时任务；P0-02 的真实约束字段、实际轨道回读、无匹配轨兜底和用户 override 语义保持不变。本项没有修改 Media3 AAR、ABR 参数、LoadControl、缓存、预载、MPV/IJK 或 native，也没有把无设备条件下的异常注入描述成真实多码率、热状态或 codec 故障端到端验证。

E-05 已把单一 Media3 滑动估计扩展为路径感知的双窗口吞吐输入，但没有重新接管选轨。自动档使用包装后的 `DefaultBandwidthMeter` 保留 Media3 的国家/网络类型首次先验、TTFB、TransferListener 与事件契约，并把 effective estimate 继续交给原生 ABR；非自动档保持原带宽计。12 秒短窗口负责快速收紧，60 秒长窗口使用按传输时长加权的调和均值并配合近期预测误差谨慎恢复；32KiB/100ms 以下短样本、乱序、旧会话和非完整网络速度样本不参与控制，样本队列上限为 64。升级至少需要 4 个可信长期样本、15 秒覆盖、预测误差不超过 500‰，每 5 秒最多增加 15%；窗口过期后只允许向 Media3 raw estimate 收紧，不能凭过期状态升级。

路径可信度继续遵守 F-02/F-04 的证据边界：远程直连可高置信度升降，LAN 最高中置信度；VPN、UNKNOWN 和并发预载只能收紧，外部 loopback、本地资源和 opaque upstream 完全不能作为控制样本。App 自有本地服务能看见 upstream 路径不代表播放器带宽计测到了 upstream 吞吐，当前本地腿因此不能驱动升档；只有显式提供真实 upstream 传输腿样本时才允许恢复。进程级 network generation 会在 F-04 网络回调时原子切断跨链路样本，网络切换后的较高 Media3 raw 先验也只能保持或收紧旧 effective，不能绕过长期样本门槛直接升级。两类预载协调器共同标记 `PreCache` 与 Media3 preload，正常 HLS 音视频并发仍按 Media3 语义聚合。实际 Format 切换会持续重算 E-01 target；新增吞吐遥测只记录估计值、样本数、预测误差、可信枚举、竞争状态和动作，不记录 URL、host、路径或异常正文。当前只完成 Mobile/Leanback arm64 各 613 个单测与双端 Debug APK 构建；没有连接设备，真实 HLS/DASH、App upstream、VPN/代理、网络切换和窗口阈值校准仍待端到端验证。

E-06 已把自动档固定起播值和全局重缓冲值改为协议/分片/链路/趋势共同约束的会话阈值。纯策略按本地、Progressive、HLS/DASH、RTSP/RTMP、VOD/live/LL-live、segment/part/hold-back、外部 loopback/opaque upstream 选择保守基线；有清单边界时按完整 segment/part 取整，LL-live 同时服从 hold-back 与 Media3 live offset。本地保持 500ms/1 秒，Progressive 通常不低于 1.5/3 秒，外部 loopback 或 opaque upstream 不低于 3/5 秒；UNKNOWN 或样本不足沿用已有自动会话值，不猜测更快门槛。

风险判断复用 E-05 effective/短窗/长窗吞吐、预测误差和路径可信度，并结合媒体需求、最近可信 buffer slope、按分片动态生成的趋势最小窗口与 time-to-empty。吞吐比下降、短窗骤降、高预测误差、近期重复重缓冲或预计 buffer 在警戒窗内耗尽会立即提高安全门槛；放宽要求可信路径、至少 4 个长期样本和 15 秒覆盖、误差不超过 250‰、吞吐余量至少约 1.8 倍、无预载竞争和稳定 buffer 证据，再连续稳定 30 秒后每 15 秒最多降低一层。网络 generation 重置、过期/UNKNOWN 事实只能保持或收紧，不能放宽。

每次 startup/rebuffer episode 会锁定首次门槛，等待过程中出现的新风险只影响下一次决策，避免反复抬高导致永久无法 READY；晚到的 live offset/hold-back 硬上限只允许向下收窄当前 episode，不允许向上移动。READY、Seek/位置不连续和会话替换会安全解锁或作废。进入 BUFFERING 前保存最后可信趋势快照，使重缓冲前 time-to-empty 不被 reset 清空；Seek 后旧趋势不复用。动态门槛继续保留 E-01 target-bytes 提前恢复、E-02 Progressive 3 秒救援上限、倍速与 live offset 语义。原全局持久化重缓冲先验已由 E-07 替换为隔离、过期的会话先验。

E-07 已将 EXO 重缓冲学习从全局两个偏好值改为进程级会话协调和版本化条目存储。学习键包含 Android 当前网络实例的隐私摘要、有效上游路径、协议以及 VOD/live/LL-live 类型；网络摘要来自 `Network.getNetworkHandle()` 的 24 位 SHA-256 短值，不读取或保存 SSID、URL、host、IP 或文件路径，也不在日志中输出摘要本身。App 内部服务只有 upstream 可见时才映射到真实 LAN/远程路径；本地资源、外部 loopback/opaque upstream、UNKNOWN 维度和 OTHER/LOCAL 协议不建立持久桶，避免不可见上游继续相互污染。

持久容器与条目版本均为 1，TTL 为 14 天，最多 32 条并按更新时间回收最旧条目；损坏行、不兼容版本、过期条目以及超过当前时间 5 分钟的未来记录会被清除。条目只保存门槛、clean streak、样本数、严重度和更新时间，旧的全局学习键不迁移并自动删除。当前会话重缓冲仍可即时提高 E-06 门槛，但持久提交延后到已进入 READY 的会话结束；未 READY、重置或取消只丢弃。迟到的清单、路径和协议事实可补绑定，只有尚无当前会话风险证据时才加载匹配先验；网络 A→B→A、路径、协议或资源类型变化会把会话标记为不稳定并禁止写入，旧 trace 结束也不会覆盖新会话当前阈值。

新增学习日志只记录动作、网络 known/unknown、路径/协议/资源枚举、阈值和样本数，`NetworkSnapshot` 的字符串表示同样不暴露摘要。新增/扩展 27 个专项用例后，Mobile/Leanback arm64 各 666 个单测及双端 Debug APK 构建通过；ADB 无连接设备，因此真实多网络切换、跨重启网络句柄复用、14 天墙钟过期、长时学习收敛、首帧和重缓冲改善仍待设备端到端验证。网络句柄随系统网络实例变化，当前设计以隐私和避免串扰优先，代价是断线重连或系统重建网络后可能形成新桶、样本更稀疏。本项没有修改 ABR、E-06 动态阈值算法、预载、缓存、MPV/IJK 或 native 参数。

E-08 已将 EXO 自动预载从“单一带宽估计加 buffer”的局部策略改为前台优先的会话状态机。输入直接复用 E-05 effective/短窗/长窗吞吐、长期样本/窗口、预测误差、路径可信度和预载竞争，并叠加当前媒体需求、buffer slope/time-to-empty、loading、重缓冲、内存门控以及 available/validated、metered/roaming、Data Saver、Battery Saver 和 thermal。明确的前台风险、计费/漫游/省电/严重热状态、内存暂停、网络不可用/未验证、吞吐不足或危险 time-to-empty 会进入 0 线程；UNKNOWN、过期证据、VPN/App 本地腿、thermal moderate、高预测误差或余量不足使用 1 线程 10 秒；显式安全证据连续稳定 20 秒后使用 1 线程 20 秒。2 线程 30 秒仍是实验上限，至少要求可信路径和中等置信度、4 个长期样本/15 秒覆盖、误差不超过 500‰、effective ratio≥3.0、短/长窗均有余量、buffer≥20 秒、趋势不下降、unmetered/validated、Data Saver disabled、正常电源/热状态，并持续稳定 30 秒。外部 loopback 不信任本地腿吞吐，始终最多 1 线程；证据不足为 10 秒，只有前台 buffer、趋势和系统事实持续安全才保留既有 40 秒范围。

系统条件通过完整 SessionToken 过滤后投递到播放器 Handler；网络变化和计费/Data Saver/省电/热风险会立即重评。若新预算减少线程、缩短范围或暂停，当前 helper 任务只取消一次，执行器先降至单线程，流量 registration 全出口释放，并重新经过恢复 buffer 水位；网络传输不持有进程全局锁。fast 状态不会仅因自己的预载 registration 产生周期震荡，手动预载仍保持用户固定线程和时长。决策遥测在既有 12 输入上限内压缩记录吞吐窗口、误差/路径、buffer 风险及系统状态，只包含数字和枚举，不含 URL、host、网络摘要、文件路径或异常正文。新增/扩展 24 个专项用例后，Mobile/Leanback arm64 各 680 个单测和双端 Debug APK 构建通过；ADB 无连接设备，真实网盘限流/412、网络切换、系统压力、外部代理和取消后连接释放仍待真机端到端验证。本项没有修改 ABR、TrackSelector、target bytes、起播/重缓冲阈值、磁盘缓存、MPV/IJK 或 native 参数。

E-09 已为 EXO 自动档硬解 MediaCodec 建立进程级运行能力档案、播放会话隔离和版本化黑名单。档案键同时隔离 Build fingerprint、App/精确 Media3 版本、decoder、MIME/codec/profile/level、分辨率/帧率、色彩/HDR 静态信息、secure、Surface/Texture 和 tunneling；fingerprint、decoder 与 codec 只持久化摘要，URL、host、路径和异常正文不进入档案。证据缺少 decoder、有效视频规格、分辨率或 codec/profile 时直接放行而不建档。容器和条目版本均为 1，TTL 30 天，超过 5 分钟的未来时间、损坏或不兼容记录自动失效，最多保存 64 条并优先保留黑名单；系统、App 或 Media3 版本变化会自然形成新环境键，允许重新验证。

运行策略区分“能启动”和“已稳定”：首帧只累计成功事实，不清除失败；至少稳定播放 30 秒、无 recoverable codec error 且掉帧不超过 23 才清除连续失败。只有 decoder 初始化、查询或运行解码的致命错误形成失败样本，掉帧和 recoverable error 不能单独拉黑；同一精确组合在一次播放只计一次，首次失败仅隔离当前会话并最多重建一次，连续两次播放失败才持久排除。原 tunneling 回退先执行，之后的通用重试可让 Media3 选择其他硬件 decoder 或自适应组内较低规格轨道；没有替代 decoder/轨道时不会虚假宣称已恢复。初始化异常若包含多个 Media3 fallback decoder，只归因首个明确项，避免一次终止错误同时污染多个档案。

运行黑名单通过自定义 `MediaCodecVideoRenderer` 的 decoder 列表过滤接入，保留既有异步 codec adapter、duration-to-progress、late input drop 和 decoder fallback 设置；非自动档、软解、MPV/IJK、Media3 AAR 以及现有 Dolby Vision → HDR10 renderer 均不改变。本项只解决“系统静态声称支持，但 decoder 明确报错”的负向证据，不做“系统未声明但实际可能支持 Dolby Vision”的正向探测，也没有帧像素/颜色正确性检测。若 decoder 不报错、不明显掉帧却输出绿屏，本项无法自动识别或自动切回 HDR10，不能把单测与构建结果描述成绿屏保护。新增 29 个专项用例后，Mobile/Leanback arm64 全量单测各 709 个及双端 Debug APK 构建通过；ADB 无连接设备，真实厂商 codec、DRM secure、Surface/Texture、tunneling、替代 decoder/降轨和 Dolby Vision/HDR10 视觉结果仍待端到端验证。

E-10 已新增纯 `ExoRtspLiveLagPolicy` 与会话级 `ExoRtspLiveLagController`，复用 F-02 的请求/运行分类和 F-06 的 5 秒运行采样，只在 EXO 自动档、明确 RTSP、播放器实际确认 live、已完成首帧/音频起播且仍有播放意图时工作。30 秒以上 lag 或 15 秒以上且持续以至少 500ms/s 增长需要 3 样本/10 秒确认；120 秒以上仍需 2 样本/5 秒。live offset 未知时，不把 RTSP scheme 或短 duration 当作 live edge，只允许 90 秒以上且持续增长的 forward-buffer 代理触发会话重建。

可靠 live edge 同时要求 Media3 window 为 live+dynamic、live offset 已知和 default-position command 可用，满足时最多 Seek 一次；边缘不可靠、Seek 调用失败或冷却后仍落后则用 `engine.restart(..., C.TIME_UNSET, ...)` 丢弃旧 RTSP MediaSource/队列并重连，保留 playWhenReady、用户速度、repeat、字幕样式和轨道恢复。Seek/重建冷却分别为 30/90 秒，单播放会话最多 1 次 Seek、2 次重建、总计 3 次；动作预算在进入 Media3 前提交，SessionToken、单调采样和位置不连续共同隔离迟到回调。决策遥测只记录协议/动作枚举、lag、增长率、buffer、冷却和次数，不记录 URL、host、路径或异常正文。

新增 19 个 E-10 专项用例后，Mobile/Leanback arm64 全量单测各 728 个及双端 Debug APK 构建通过，`git diff --check` 通过。ADB 无连接设备，因此未进行真实 RTSP TCP/UDP 服务端、弱网后 live edge、Seek 是否真正跳到最新、长时 native RSS/队列增长、重连风暴或用户回看行为端到端验证。当前 `getTotalBufferedDuration()` 只是 live offset 不可用时的异常增长代理，不能被描述为真实内存泄漏检测。本项没有修改 MPV/IJK、HLS/DASH、ABR、LoadControl、缓存、预载、RTSP transport、Media3 AAR 或 native 参数。

M-01 已让 MPV 自动档脱离推荐固定档并进入独立的初始控制器。新媒体装载和 MPV 重建时，策略按当前会话的可用内存、协议、live/VOD 与双腿路径事实选择 24/48/64MiB forward、0 back 的保守基线：内存快照未知/过期、low-RAM、小 heap、低 Java headroom、MODERATE/CRITICAL 压力或系统 low-memory 使用 24MiB；普通可用内存事实使用 48MiB；只有 heap≥512MiB、Java headroom≥256MiB、系统安全余量≥768MiB 且压力 NORMAL 时允许 64MiB。本地资源上限 24MiB，live、RTSP/RTMP、外部 loopback 或 opaque upstream 上限 48MiB；当前没有按媒体码率扩到 96/128/192MiB。

控制器以完整 `SessionToken` 隔离动作，先提交状态再离锁调用 MPV。首次 native context 尚未创建时只暂存 `demuxer-max-back-bytes` 与 `demuxer-max-bytes`，初始化后、媒体加载前应用，并在 context 替换后继续复用，避免对未初始化 JNI 写属性；已初始化 context 可直接应用。`mpv.conf优先` 在策略层和 native 选项层双重抑制，退出自动档或被抑制会清除暂存；`cache-secs`、readahead、重缓冲、HLS variant、预载、速度、字幕、LUT、shader/filter、推荐/兼容/轻量/自定义档以及 EXO/IJK 均不改变。新增 `mpv-cache` 遥测只记录枚举、容量和动作，首次暂存记为 REQUESTED；setter 成功不等于属性读回，更不能证明 packet pool 或 RSS 已立即回落。

新增 26 个 M-01 专项用例后，Mobile/Leanback arm64 全量单测各 754 个及双端 Debug APK 构建通过，`git diff --check` 通过。ADB 无连接设备，真实 MPV 高码率、`mpv.conf` 覆盖、native 属性读回、context 替换和 RSS/PSS 趋势仍未端到端验证。播放中的需求/容量扩缩、压力立即降级、迟滞恢复和 96/128/192MiB 层级仍由 M-02 实现，本项只交付初始基线与状态机骨架。

## 六、内存预算与产品起始值

### 6.1 先算媒体需求，再算设备上限

```text
平均需求字节 = averageBitrate / 8 × targetSeconds
突发需求字节 = peakOrObservedP90Bitrate / 8 × burstWindowSeconds
payload需求 = max(平均需求字节 × 1.10～1.20, 突发需求字节)
有效缓存目标 = min(payload需求, 内核guard, 当前设备会话预算)
```

注意：payload 不等于总进程内存。它不包含 packet metadata、MediaCodec/解码队列、图形 buffer、字幕/LUT、音频、JNI 和播放器对象。

| 媒体码率 | 30 秒 payload，按 1.15 | 二进制约值 |
|---:|---:|---:|
| 8Mbps | 34.5MB | 32.9MiB |
| 20Mbps | 86.3MB | 82.3MiB |
| 50Mbps | 215.6MB | 205.6MiB |
| 100Mbps | 431.3MB | 411.3MiB |

这说明 50～100Mbps 原盘无法同时满足“30～60 秒”和约 200MB 内存 guard；正确动作可能是缩短内存缓冲目标、依赖安全磁盘缓存、提高上游供给或报告资源不可持续，而不是继续突破内存。

### 6.2 保守产品起始值，不是最佳值

| 设备状态 | EXO target 起点/通常上限 | MPV forward 起点/通常上限 | MPV back | IJK 有限队列 | 自动预载 |
|---|---:|---:|---:|---:|---|
| low-RAM 或 heap 128～192MiB | 16～24 / 32～48MiB | 24～32 / 48MiB | 0 | 4～8MiB | 默认 0 |
| heap 256～384MiB、无压力 | 48～64 / 96～128MiB | 48～64 / 96～128MiB | 默认 0；按需 16MiB | 8～15MiB | 0→1 |
| heap ≥512MiB、持续有余量 | 64～96 / 128～192MiB | 64～96 / 128～192MiB | 默认 0；按需 16～32MiB | 15MiB | 0→1，极佳时实验 2 |
| lowMemory/trim/余量不足 | 回最低层并禁止扩张 | 24～32MiB | 0 | 4MiB 且 `infbuf=0` | 立即停止 |

192MiB 以上仅在真实码率需求、稳定内存余量和长时真机测试同时证明必要时实验；256MiB 不进入通用自动默认。表中所有值都需要按机型遥测重新校准。

### 6.3 设备会话预算

建议同时满足：

```text
EXO预算 ≤ Java heap limit - current Java used - Java reserve
native预算 ≤ 系统可用余量 - 系统保留 - 当前进程非缓存占用估计
总播放器预算 ≤ 会话启动基线 + 允许增长量
```

不要仅凭总 RAM 或 `availMem≥固定GiB` 扩张。预算控制器必须具备：

- 进入播放、切换内核/轨道和发生压力事件时重算。
- 扩张小步进行，缩容立即下发；MPV 缩容后继续验证真实释放。
- Java/native/磁盘三套预算独立记账。
- 内存压力时停止预载优先于牺牲前台播放缓存。

### 6.4 系统压力动作

| 触发 | 立即动作 |
|---|---|
| `onLowMemory`、`lowMemory=true`、`availMem≤threshold` | 停预载、back=0、禁升档、内存缓存回最低层 |
| 当前 trim level 表示后台/UI hidden | 释放可重建 UI/诊断资源；前台播放按可见状态判断，不机械停播 |
| API<34 收到 running low/critical | 同低内存动作；API≥34 不依赖此事件 |
| Java heap headroom 接近 reserve | EXO 停加载扩张，释放 allocator/preload 可回收资源 |
| native/RSS 持续增长且 buffer 不增长 | MPV/IJK 缩容或重建异常会话，记录诊断 |
| thermal=MODERATE | 禁升级、禁 2 线程预载、禁自动插帧 |
| thermal=SEVERE+ | 停预载，降低软解负载/轨道，优先已验证低功耗路径 |
| Battery Saver/Data Saver/metered/roaming | 禁快速预载；是否允许普通预载服从用户数据策略 |

## 七、按资源场景的起始策略

| 场景 | 前向目标起点→通常上限 | 起播/重缓冲起点 | 核心策略 |
|---|---|---|---|
| 本地文件 | 1→15 秒 | 0.5～1/1 秒 | 无网络预载，按需 back |
| 稳定 LAN | 5→30 秒 | 1/1～2 秒 | 1 线程即可，真实吞吐充足再扩张 |
| 网盘 progressive Range | 20～30→60 秒 | 1.5～3/3～5 秒 | 单码率；依赖 slope、Range 和代理上游 telemetry |
| HLS/DASH VOD | 30→50 秒并对齐 segment | 1/2～3 秒 | Media3 ABR 主导，自定义层只给约束 |
| 普通 HLS/DASH live | 约 3×target duration→清单允许上限 | 1～2/2～3 秒 | 跟踪 live lag，不预载、不保留 back |
| LL-HLS | `PART-HOLD-BACK` 起步 | 按 part/segment 边界 | 服从清单，过近时宁可增延迟避免 stall |
| RTSP/RTMP | 小而有限 | 协议实测 | 检测 lag，超限跳最新/丢旧/重建；禁止 IJK infbuf |
| 外部 loopback | 20～30→60 秒 | 3/5 秒 | 不信任本地腿吞吐，默认不预载 |
| 软件解码 | 15→30 秒 | 1～2/2～3 秒 | 依据真实掉帧/thermal 降分辨率，不用缓存掩盖解码瓶颈 |
| 4K/HDR 硬解 | 20～30→内存 guard 允许值 | 2/3～5 秒 | 真实 decoder 档案和峰值码率决定 |
| 高频向后 Seek | forward 不变 | 不变 | back 从 15 秒/16MiB 小步开启，压力时归零 |

秒数同样是起始策略。HLS/DASH 应至少对齐完整 segment/part，不能请求一个无法通过分片边界实现的精确时间目标。

### 7.1 回看缓存

- 默认 back=0，符合 Media3 默认，也避免 MPV 默认持有历史包。
- 10 分钟内至少 2 次明显向后 Seek 后，实验开启 15 秒或 16MiB。
- 只有持续行为和内存余量同时成立才扩到 30 秒或 32～64MiB。
- 10 分钟无向后 Seek、进入 live、不可 Seek、trim/lowMemory 时归零。
- MPV 必须考虑 forward donation，UI 展示和预算用 forward+back 潜在总量。

### 7.2 预载

- ratio `<1.15` 或 buffer 负趋势：暂停。
- 恢复要求 ratio `≥1.40`、前台达到安全线并稳定 10～15 秒；这些是产品起点，需真机调参。
- 普通预载：1 线程、10～20 秒。
- 2 线程仅在 ratio `≥3.0`、buffer `≥20 秒`、稳定 `≥30 秒`、可控直连/App 服务、unmetered、非漫游、非 Data/Battery Saver、内存/热均安全时实验。
- 重缓冲、Seek、underrun、trim、lowMemory、thermal≥MODERATE、网络切换时立即取消。
- 外部 loopback 默认 0，除非代理显式提供真实上游 telemetry 和独立优先级/取消能力。

### 7.3 多码率选择与防抖

对 HLS/DASH：

- 首次使用 Media3 保守先验，不用设备理论码率抬高。
- 降档依据 buffer 风险、可信吞吐和当前实际轨道，由原生 ABR 执行。
- 自定义层只在 codec/显示/热/计费/运行黑名单上提供上限。
- 升级必须满足 buffer 安全、长期吞吐余量、预测误差可控、20～30 秒无重缓冲，并设置 30～60 秒冷却期。
- 发生重缓冲可立即收紧约束；恢复慢于降级，避免 FESTIVE 所强调的切换震荡。

对 progressive/REMUX：没有多码率 variant，不执行“降一级码率”的虚假动作。

### 7.4 VOD 网络保护降速

当前网络保护已限制为 EXO VOD、用户 1.00x、非 tunneling/直通等场景，但产品语义仍需收紧：

- Media3 的 0.97 下限来自直播延迟控制，不能为 VOD 降速背书。
- 自动档默认不改变用户速度；有多码率时优先 ABR。
- 若保留单码率救援，必须用户显式允许，UI 明确正在改变片长，并设置短时、可撤销、严格下限。
- 0.85 会让两小时内容增加约 21 分钟，不应成为无感知的通用自动策略。

## 八、实施优先级

### P0：先修正确性与资源安全

1. 取消 HLS 代理无条件删除低 variant；保留 `BANDWIDTH` 与 `AVERAGE-BANDWIDTH` 两套语义。
2. 修正 EXO `capByBandwidth()` 写入 `maxVideoBitrate`，并回读实际选中 Format；随后重构其与原生 ABR 的职责。
3. 移除 20～40Mbps 乐观初值，恢复 Media3 保守先验。
4. IJK 自动/稳定场景默认 `infbuf=0`，在有限队列下重新验证直播水位。
5. 修正 EXO 和 MPV HLS 代理磁盘预算为“当前可用空间减保留空间”，处理 ENOSPC。
6. 修正 VBR 估计：format 值不能屏蔽可信 p90；限制 byte slope 只用于单连续流。

### P1：建立共享事实层

实现 `PlaybackEnvironment/PlaybackAutoContext`：

- 内存事件、Java/system 快照、低成本 native 指标、热/省电/计费网络。
- 当前显示模式、真实轨道、decoder 运行档案。
- 协议/live/Range/segment/part/播放路径分类。
- 可信吞吐、预测误差、buffer slope、time-to-empty、live lag、重缓冲、掉帧、Seek。
- 每项输入的置信度、时间戳和来源。

### P1：完善 EXO 自动

- streaming/local LoadControl 分离。
- 多码率默认字节优先；高码率单轨仅在硬保护下受控时间优先。
- target bytes 使用需求、约 200MB guard、设备预算三者最小值。
- 运行 codec 档案和版本化黑名单。
- RTSP live lag 恢复策略。
- 对 50/75/100ms early scheduling 和 duration-to-progress 做问题设备 A/B，不发布全局常量。
- 重缓冲学习按网络、路径、协议、资源类型隔离并过期。

### P1：实现 MPV 自动缓存控制器

- 从 24/48/64/96MiB 保守层级起步，按真实需求扩到 128/192MiB；更高只实验。
- 运行时更新 max/back bytes，缩容后验证真实 forward/total/PSS。
- back 默认 0，按 Seek 行为开启。
- 消除 `cache-secs/readahead-secs` 重复语义；实验小 hysteresis 降低功耗。
- HLS 根据可信吞吐选初始 variant；持续 underrun 时明确重载/重启降档。
- 区分 native packet cache 与代理磁盘缓存预算。

### P2：实现 IJK 场景和反馈控制

- 解析 HLS/DASH 清单识别 VOD/live/LL-live。
- 所有自动场景使用有限 4/8/15MiB 队列，禁止 `infbuf` 绕过上限。
- 水位按 target/part duration、live lag 和重缓冲反馈设置。
- picture queue 默认 3，高分辨率不盲目增到 5/8。
- 记录重缓冲、掉帧、native 增长和 decoder 错误，建立内核/软解回退。
- RTSP/RTMP 延迟超限时丢旧或重建，不能只累积 buffer。

### P3：逐步移除固定档位

1. 自动档覆盖并验证推荐档成功场景。
2. 将“均衡/推荐”合并到自动，先保留兼容、轻量和自定义作为回退。
3. 完成 low-RAM、普通/高内存 TV、直播、网盘 Range、loopback、软解、4K/HDR 和 codec 异常验收后，再评估移除轻量。
4. 兼容档最后移除，因为它仍承载厂商 codec、输出和协议异常的固定回退价值。

## 九、遥测与验收

### 9.1 场景矩阵

| 场景 | 必测结果 |
|---|---|
| low-RAM 设备 | 无 OOM/系统杀进程，压力事件后能停止非必要工作 |
| 普通 1080p TV | 起播、重缓冲、内存、掉帧不劣于官方/原版基线 |
| 4K/HDR TV | codec/显示判断正确，VBR 峰值不突破 guard |
| HLS/DASH 多码率 | 原生 ABR 可降可升，自定义约束不与之打架 |
| 网盘 progressive/REMUX | slope 只用于适用路径，不依赖不存在的 ABR |
| 外部 loopback/VPN | 不误信本地腿吞吐，不让预载抢前台 |
| HLS/LL-HLS live | target/part/hold-back 生效，延迟超限能恢复 |
| RTSP/RTMP 长时直播 | 不无限增内存，lag 超限可回最新或重建 |
| IJK realtime | `infbuf=0`，有限队列下连续播放无异常增长 |
| 软件解码/热压力 | 能区分解码瓶颈与网络瓶颈并降负载 |
| 高频 Seek | back 按行为开启，压力时自动关闭 |
| 存储接近满 | 保留空间不被侵占，写失败能停预载和 prune |
| 厂商 codec 虚报能力 | 失败档案能回退并在版本变化后重新验证 |

### 9.2 统一指标

- 首帧时间、起播缓冲。
- 5/30/120 秒 forward buffer、字节、变化斜率。
- 短/长窗口吞吐、预测误差、上游/本地腿来源。
- 平均/峰值媒体码率、估计来源和置信度。
- 实际选中 Format、variant 切换次数和原因。
- 重缓冲次数、总时长、最长单次、live lag。
- 掉帧、帧提前/延后分布、decoder error。
- Java used/limit、native 指标、诊断 PSS、system avail/threshold、trim/lowMemory。
- thermal、Battery Saver、metered/roaming/Data Saver。
- 实际 decoder/hwdec/VO/output、显示模式、运行能力档案命中。
- 预载线程、流量、取消原因；磁盘 available/reserve/cache used 和写错误。
- 自动决策输入、置信度、前值、目标值、原因、被抑制原因。

### 9.3 上线门槛

- 同一资源随机网络 trace 下至少与固定档做 A/B，不只测单次“能播”。
- 统计 P50/P95 首帧、重缓冲率/总时长、峰值内存、掉帧和 live lag。
- 按设备/decoder/协议分组，不能用总体平均掩盖某类电视退化。
- 所有实验参数可远端或本地快速回滚，黑名单有版本失效策略。
- 自动档只有在上述矩阵中稳定优于或至少不劣于固定档，才继续移除其他档位。
