# 播放性能自动档判断依据与最佳参数方案

- 日期：2026-07-23
- 代码基线：`beta` / `36bb737910` / `playback-optimization-item-92`
- Media3：`1.11.0-alpha01-fongmi`
- 适用内核：EXO、MPV、IJK
- 目标：把现有多个固定性能档位逐步收敛为一个有真实设备、资源和运行反馈依据的“自动”档位

## 一、结论先行

当前“自动”档位尚未形成三个内核统一的自动控制器：

1. EXO 已经具备真实下载吞吐、媒体码率、缓冲趋势、重缓冲、掉帧、播放路径和预载状态机，方向基本正确，但真实系统内存、当前进程 native/PSS、热状态、真实轨道 codec 和当前输出模式仍未进入完整决策。
2. MPV 目前只有输出模式具备真正的自动判断；缓存、回看缓存、HLS 码率、重缓冲和预载仍主要使用“推荐/均衡”固定值。
3. IJK 的自动场景主要通过 URL scheme 判断 RTSP、RTP、UDP、RTMP，普通 HLS 直播不会被识别为直播，核心缓冲参数也仍是固定默认值。
4. EXO 并非完全没有检测内存：它已经读取 `isLowRamDevice()` 和 Java heap 上限。但它没有读取系统真实可用内存、系统低内存阈值、进程 native/PSS 和热状态；MPV/IJK 连同等级的内存预算都没有。
5. 当前最先要修复的不是继续微调固定档位，而是修正会破坏自动判断基础的确定性问题：HLS 代理强制最高码率、EXO 带宽上限写错字段、初始网络估计过度乐观。

自动档应遵循以下原则：

- 保守起步，测得真实能力后再扩张。
- 降级快、升级慢；严重风险立即降级，升级必须持续稳定 20～30 秒。
- 码率不足时优先降轨，而不是无限扩大缓存。
- 缓存字节由真实媒体码率和目标秒数计算，再受 Java heap、系统可用内存、native/PSS 和设备档位的共同上限约束。
- 回看缓存和预载默认关闭或最小化，只在用户行为和运行状态证明有收益时开启。
- 用户明确选择的字幕、LUT、插帧、精确 Seek、播放速度和 `mpv.conf` 优先级不应被自动档擅自覆盖。

## 二、哪些参数应该自动判断

### 2.1 必须自动判断

| 参数 | 必要输入 | 目标 |
|---|---|---|
| 前向缓存字节 | 媒体码率、目标秒数、Java heap、系统可用内存、native/PSS | 避免固定 64/128/256MiB 对所有资源一刀切 |
| 前向缓存秒数 | 本地/远程、VOD/live、Range、HLS/DASH、吞吐波动 | 在起播速度、稳定性和内存之间平衡 |
| 起播与重缓冲阈值 | 首次吞吐、缓冲趋势、历史重缓冲、直播延迟目标 | 稳定资源快速起播，弱网资源避免反复缓冲 |
| 自适应码率上限 | 可信吞吐、码率分布、buffer slope、time-to-empty | 最高轨码率不超过安全吞吐 |
| 分辨率、帧率和 codec 上限 | 当前真实轨道、MediaCodec 能力、PerformancePoint、当前显示模式 | 不因设备“理论最大模式”错误选择过高轨道 |
| 硬解/软解回退 | 实际 decoder、首帧、解码错误、掉帧、热状态 | 优先硬解，失败可验证回退 |
| MPV 输出模式 | TV/手机、硬解、分辨率、字幕、LUT/滤镜、GPU 自定义处理 | 高规格无特效资源走电视直出，其余走 GPU |
| 预载开关、线程和时长 | 前台缓冲、吞吐/码率比、播放路径、重缓冲、内存和热状态 | 前台播放优先，0～2 线程动态变化 |
| 回看缓存 | 向后 Seek 频率、内存余量、资源可 Seek 能力 | 默认 0，用户确实频繁回看后再开启 |
| IJK 场景 | HLS 清单、DASH 类型、RTSP/RTMP、是否存在 ENDLIST、live offset | 不再仅依赖 URL scheme |
| probe 和 RTSP 策略 | 容器、协议、首次探测结果、失败原因 | 已知格式快速探测，失败后升级完整探测或切换传输 |
| 内存和热降级 | `lowMemory`、`threshold`、trim、PSS/native、thermal | 内存/热压力出现时立即停止非必要工作 |
| 磁盘缓存容量 | 剩余空间、资源类型、缓存命中率 | 防止固定大缓存挤占存储空间 |

### 2.2 可以自动提供默认值，但必须允许用户覆盖

- 音频直通：按电视/功放能力和音频格式自动启用，失败后回退 PCM。
- AAC 优先：只应作为音频兼容性回退，不应成为所有设备的固定偏好。
- 帧率匹配：自动档可默认“仅无缝”，非无缝黑屏切换应尊重用户选择。
- frame drop：默认使用播放器官方安全模式，检测持续解码过载后再增强。
- RTSP TCP/UDP：TCP 作为稳定默认，低延迟明确需要或 TCP 失败时再尝试 UDP。
- 软件解码降负载：只在真实软解、掉帧或热压力出现时启用。

### 2.3 不应被自动档主动覆盖

- 字幕选择、字幕渲染需求。
- LUT、画面滤镜、插帧等用户视觉偏好。
- 用户播放速度。
- 精确 Seek 偏好。
- `mpv.conf` 与播放性能配置的优先级。
- 用户明确锁定的清晰度或“原版”质量选择。

自动控制器应把这些偏好作为约束条件参与判断，而不是为了性能直接关闭。

## 三、当前实现审计

| 应自动判断的项目 | 当前 EXO | 当前 MPV | 当前 IJK | 完备度 |
|---|---|---|---|---|
| 内存容量 | `isLowRamDevice + Runtime.maxMemory` | 固定缓存档位 | 固定 4/8/15MiB | EXO 部分完备，MPV/IJK 不完备 |
| 系统真实可用内存 | 未读取 | 未读取 | 未读取 | 缺失 |
| native/PSS | 未读取 | 未读取 | 未读取 | 缺失 |
| 热状态 | 未读取 | 未读取 | 未读取 | 缺失 |
| 真实吞吐 | 已使用 Media3 BandwidthMeter | 已采集但未驱动配置 | 未形成闭环 | EXO 较好 |
| 缓冲趋势 | 已使用快慢斜率和 time-to-reserve | 已采集缓存状态但未决策 | 仅缓冲事件/百分比 | EXO 较好 |
| 重缓冲自学习 | 3～15 秒，且全局持久化 | 固定 2 秒 | 固定水位 | EXO 部分完备 |
| 自适应清晰度 | 有带宽/掉帧降级，但带宽 cap 字段错误 | HLS 固定初始选轨 | HLS 固定初始选轨 | 存在关键错误 |
| 播放路径 | 区分直连、App 服务、外部 loopback | 有网络恢复边界 | 通过同一 HLS 代理 | 部分完备 |
| 预载 | 0～2 线程、10～40 秒状态机 | 固定 1 线程，主要在 Seek 后触发 | 固定 1 线程 | EXO 较成熟 |
| 输出模式 | Surface/Texture、显示模式、tunneling | Surface Direct/GPU 自动切换 | 固定 Surface | MPV 输出策略较成熟 |
| codec 能力 | 固定以 HEVC 探测设备能力 | 运行时硬解失败回退 | 固定开关 | 未按真实轨道完整判断 |
| live/VOD | Media3 能识别协议，但自动策略未完整分层 | HLS 代理能识别 VOD 清单 | URL scheme 判断 realtime | IJK 明显不足 |
| 内存压力回调 | `onTrimMemory()` 仅日志 | 无动作 | 无动作 | 缺失 |

### 3.1 自动档入口并未统一为自动控制器

`PlaybackPerformanceSetting.applyAuto()` 中：

- EXO 调用 `ExoPerformanceSetting.applyAuto()`。
- MPV 调用 `MpvPerformanceSetting.applyRecommended()`。
- IJK 调用 `IjkPerformanceSetting.applyRecommended()`。

因此 MPV/IJK 自动档目前与推荐/均衡档基本相同，只是 MPV 输出模式内部另有自动状态机。

证据：`app/src/main/java/com/fongmi/android/tv/setting/PlaybackPerformanceSetting.java:63`。

### 3.2 EXO 内存预算已存在，但不是完整真实内存判断

`ExoBufferBudget` 当前读取：

- `ActivityManager.isLowRamDevice()`。
- `Runtime.getRuntime().maxMemory()`。
- `getMemoryClass()`、`getLargeMemoryClass()` 和 `largeHeap` 标记。

当前规则：

- low-RAM：Java heap 的 20%，预留 48MiB。
- 普通设备：Java heap 的 30%，预留 64MiB。
- 最低 16MiB，最高 256MiB。

典型结果：

| Java heap | 当前自动目标字节 |
|---:|---:|
| low-RAM 128MiB | 25.6MiB |
| low-RAM 192MiB | 38.4MiB |
| 普通 256MiB | 76.8MiB |
| 普通 384MiB | 115.2MiB |
| 普通 512MiB | 153.6MiB |
| 普通 1GiB | 256MiB 封顶 |

不足之处：

- `memoryClass/largeMemoryClass/largeHeap` 目前只保留到诊断对象，不改变预算；对应测试明确验证了这一行为。
- 未读取 `ActivityManager.MemoryInfo.totalMem/availMem/lowMemory/threshold`。
- 未读取 `ActivityManager.getProcessMemoryInfo()`、`Debug.MemoryInfo.getTotalPss()` 或 `Debug.getNativeHeapAllocatedSize()`。
- `onTrimMemory()` 只记录日志，没有通知三个播放器缩减缓存、关闭回看和停止预载。
- MPV 的 demux 缓存主要属于 native 内存，只看 Java heap 无法决定其安全值。

### 3.3 EXO 自动档的字节预算不是严格硬上限

EXO 自动档通过 `ExoLoadControlPolicy.prioritizeTime()` 强制时间优先。Media3 在未达到最小缓冲时间时，即使 target bytes 已达到，也可能继续加载。

当前定制 Media3 虽然增加 heap 压力保护，但停止条件仍很晚：

- heap 尚未扩张到 `maxMemory` 时继续允许加载。
- heap 已扩张到上限后，剩余空间约低于 4% 才阻止继续加载。

因此 `ExoBufferBudget` 更接近软预算，而不是严格内存上限。自动档应恢复流媒体 `prioritizeTime=false`，或者增加更早的系统内存和进程内存硬保护。

### 3.4 EXO 初始网络估计严重偏乐观

当前实现：

```text
Wi-Fi/Ethernet = max(设备目标码率 × 2, 20Mbps)
5G             = max(设备目标码率 × 1.5, 15Mbps)
4G             = max(设备目标码率, 8Mbps)
```

4K 能力设备在 Wi-Fi/Ethernet 上会直接以 40Mbps 作为初始估计。Media3 当前依赖版本的内置初值大致为：

- Wi-Fi/Ethernet：0.86～4.3Mbps。
- 4G：0.68～2.5Mbps。
- 5G NSA：0.98～4.7Mbps。
- 5G SA：1.0～2.7Mbps。
- 未知网络：1Mbps。

当前值可能比官方最高分组仍高 5～10 倍，容易在首次吞吐尚未测出前选择过高轨道。自动档应优先使用 Media3 内置国家/网络分组初值，或最多使用保守的产品上限，不能把 Wi-Fi 等同于真实高速网络。

另外，当前 `setSlidingWindowMaxWeight(4000)` 是 Media3 默认 2000 的两倍，会提高平滑性但降低弱网恶化时的反应速度。自动策略应单独维护短窗口和长窗口，而不是只扩大一个滑动窗口。

### 3.5 EXO 自适应带宽上限没有真正写入 TrackSelector

`AdaptiveVideoProfileController.capByBandwidth()` 修改的是 `EnhancedVideoProfile.bitrate`，但 `applyEnhancedVideoProfile()` 真正传入 TrackSelector 的字段是 `maxVideoBitrate`。

后果：

- 计算出的“带宽安全上限”不会成为真实码率上限。
- 控制器通常只能降一级分辨率，无法精确约束同分辨率下的多档码率。

这是自动选轨前必须修复的正确性问题。

### 3.6 EXO 设备能力只预检 HEVC 和最大显示模式

当前 `detectPlaybackCapability()` 固定使用 `video/hevc` 探测解码能力；实际资源可能是 H.264、AV1、VP9、Dolby Vision 或其他 profile/level。

显示判断使用所有 supported mode 的最大分辨率，而不是当前实际输出模式。这可能导致电视当前处于 1080p 输出时仍允许选择 4K 轨道。

自动档应在轨道信息可用后按以下信息重新决策：

- 真实 sample MIME。
- codec string、profile、level、bit depth、HDR/DV profile。
- 分辨率、帧率、码率。
- secure decoder 需求。
- 对应 decoder 的 PerformancePoint。
- 当前输出模式，而不只是电视理论最大模式。

### 3.7 MPV 自动缓存仍是固定大值

自动/推荐档通过共享预设得到：

- forward cache：256MiB。
- back cache：约 128MiB。
- `cache-secs/demuxer-readahead-secs`：30 秒。
- 重缓冲等待：2 秒。
- HLS：最高码率。
- 预载：开、1 线程、20 秒。
- HLS 代理磁盘缓存：512MiB。

forward 与 back 的潜在 native 包缓存上限约为 384MiB。它不一定始终全部驻留，但对 low-RAM 和普通电视明显缺少安全依据。

MPV 已经采集以下运行信息，却没有用于自动调参：

- `cache-speed`、`raw-input-rate`。
- forward/total/file cache bytes。
- cache duration、cache end、reader PTS。
- underrun、paused-for-cache。
- 视频/音频码率、掉帧、hwdec、VO、刷新率。

这些信息足以建立 MPV 自动缓存状态机，不应继续只依赖档位常量。

### 3.8 MPV/IJK 的 HLS 自动码率被代理破坏

`MpvHlsProxy.lowerVariantLinesToSkip()` 会在 master playlist 中删除除最高分辨率/码率外的所有 variant。

后果：

- `hls-bitrate=8Mbps/15Mbps/min` 可能无效。
- MPV 官方 `hls-bitrate` 本来就只是初始固定选轨，不是动态 ABR；代理再删掉其他 variant 后，连后续重新选择的可能性也没有。
- IJK 使用同一个 HLS 代理，因此同样受影响。

在修复该问题前，MPV/IJK 的 HLS 自动码率没有可靠实现基础。

### 3.9 IJK 自动场景判断不足

当前只有以下 scheme 被认为是 realtime：

```text
rtsp / rtp / udp / rtmp
```

普通 HTTP HLS 直播不会进入直播场景。`SCENE_AUTO` 主要只影响 realtime 情况下的 `infbuf`，其余参数仍固定为：

- max buffer：15MiB。
- packet buffering：开。
- 水位：100/1000/5000ms。
- picture queue：3。
- frame drop：1。
- probe：系统默认。
- RTSP：TCP。

这些值与锁定 IJK 源码默认接近，适合作为普通 VOD 基线，但不能称为完整自适应。

## 四、可信的官方基准

网上所谓“最佳参数”不存在适合所有设备和资源的固定常数。可信基准应优先来自当前依赖版本和对应播放器官方源码，再由自动控制器按运行数据调整。

### 4.1 Media3 DefaultLoadControl

当前依赖版本默认值：

| 参数 | 流媒体 | 本地播放 |
|---|---:|---:|
| min buffer | 50 秒 | 1 秒 |
| max buffer | 50 秒 | 50 秒 |
| 起播 | 1 秒 | 1 秒 |
| 重缓冲恢复 | 2 秒 | 1 秒 |
| prioritize time | false | true |
| back buffer | 0 | 0 |

字节目标：

- muxed 默认目标约 144,310,272 bytes。
- 全轨道最大目标约 210,239,488 bytes。
- buffer segment 为 64KiB。

当前项目使用通用 `setBufferDurationsMs()`，会同时覆盖流媒体和本地播放值。应改用：

- `setBufferDurationsMsForStreaming()`。
- `setBufferDurationsMsForLocalPlayback()`。
- 对应的 streaming/local `setPrioritizeTimeOverSizeThresholds...()`。

### 4.2 Media3 AdaptiveTrackSelection

官方默认：

- bandwidth fraction：0.7。
- 升清晰度前最小缓冲：10 秒。
- 降清晰度最大缓冲参考：25 秒。
- 丢弃旧低清晰度片段后至少保留：25 秒。
- live edge 升档比例：0.75。

自动档应至少以“最高轨码率不超过可信吞吐的 70%”为基线。外部 loopback、直播或波动明显的网盘链路可进一步降至 60%～65%。

### 4.3 MPV 精确版本默认值

当前 bundled mpv 对应 `0.41.0-878-g94335ab87`：

- `demuxer-max-bytes=150MiB`。
- `demuxer-max-back-bytes=50MiB`。
- `demuxer-readahead-secs=1`。
- `cache-secs` 默认很大，通常由 bytes 限制实际缓存量。
- `cache-pause-wait=1`。
- `framedrop=vo` 是推荐默认。
- `hls-bitrate=max` 是固定初始选择，不是动态 ABR。
- `mediacodec-copy` 会把视频复制回系统内存。
- `mediacodec_embed` 功耗较低，但不能完整承载字幕、LUT 和 GPU 滤镜。

MPV 官方默认主要面向多平台，不能直接作为 Android 低内存设备的最佳值，但它说明当前统一 256+128MiB 已经明显高于原生默认，应由真实内存控制。

### 4.4 IJK 锁定版本默认值

- max queue：15MiB。
- first/next/last water：100/1000/5000ms。
- picture queue：3。
- packet buffering：开。

当前推荐档接近原生默认。自动档要做的是根据 low-RAM、直播低延迟、重缓冲和软解压力在 4/8/15MiB 与不同水位间切换。

## 五、自动决策需要的三层输入

### 5.1 静态设备层

必须采集：

- `isLowRamDevice()`。
- `Runtime.maxMemory/totalMemory/freeMemory`。
- `MemoryInfo.totalMem/availMem/lowMemory/threshold`。
- 当前进程 Java heap、native heap、total PSS。
- API 29+ thermal status 和监听器。
- 当前显示模式与所有支持模式。
- 当前真实轨道 MIME/profile/level 对应的 MediaCodec 能力和 PerformancePoint。
- 电视/功放音频能力。
- 剩余磁盘空间。

注意：

- EXO Java allocator 主要受 Java heap 限制，`Runtime.maxMemory()` 比物理总 RAM 更直接。
- MPV/IJK 的 packet cache、解码队列和 native 库占用必须同时参考系统可用内存、进程 native/PSS。
- `availMem` 是近似值，不应被当作绝对空闲 RAM；应结合 `threshold`、`lowMemory` 和趋势判断。
- PSS 获取成本高于普通字段，可在起播、切轨、每 15～30 秒以及收到 trim 时采样，不应逐帧调用。

### 5.2 资源和路径层

必须识别：

- 本地文件、LAN、直接远程 HTTP、App 内置服务、外部 loopback。
- progressive Range、HLS、DASH、RTSP、RTMP。
- VOD、普通直播、低延迟直播。
- HLS master/media playlist、`ENDLIST`、playlist type、target duration。
- DASH static/dynamic。
- 是否支持 Range、Seek、长度和时长。
- 当前选中轨道的分辨率、帧率、码率、HDR、bit depth、音频码率。
- 单码率资源还是多 variant 可切换资源。
- 代理链路是否能暴露真实上游吞吐。

外部 loopback 的本地传输速度不等于上游网盘/CDN 速度。无法看到上游时，应以 buffer slope、time-to-empty、重缓冲和代理显式 telemetry 为依据，不能直接使用 `127.0.0.1` 的瞬时读取速率升级码率或启动预载。

### 5.3 实时反馈层

建议统一采集：

- 5～30 秒窗口的 p20/p50 吞吐。
- 吞吐/媒体码率比。
- 当前 forward buffer、变化斜率和 time-to-empty。
- loading/idle、underrun、paused-for-cache。
- 重缓冲次数和总时长。
- 掉帧数量、掉帧率、解码耗时。
- 实际 hwdec、decoder、VO/output。
- 内存 trim、lowMemory、PSS/native 增长。
- thermal status。
- 用户向前/向后 Seek 行为。

## 六、建议的内存和值矩阵

缓存所需字节应先按真实媒体码率计算：

```text
所需缓存字节 ≈ (视频码率 + 音频码率) / 8 × 目标秒数 × 1.10～1.20
```

示例：

| 媒体码率 | 目标时间 | 按 1.15 余量计算 |
|---:|---:|---:|
| 8Mbps | 30 秒 | 约 34.5MB |
| 20Mbps | 30 秒 | 约 86MB |
| 50Mbps | 30 秒 | 约 216MB |
| 50Mbps | 60 秒 | 约 431MB |
| 100Mbps | 30 秒 | 约 431MB |

因此固定“256MiB + 60 秒”无法覆盖 50～100Mbps 原盘，同时也会在低码率内容上浪费内存。

### 6.1 按设备内存分级

| 设备状态 | EXO 初始/扩张上限 | MPV forward 初始/扩张上限 | MPV back | IJK max buffer | 自动预载 |
|---|---:|---:|---:|---:|---|
| low-RAM 或 heap 128～192MiB | 24～32 / 48MiB | 32 / 48MiB | 0 | 4～8MiB | 默认 0 线程；极稳定时最多 1 |
| heap 256～384MiB | 64 / 96～128MiB | 64 / 128MiB | 默认 0；按需 16～32MiB | 8～15MiB | 0→1 线程，10～20 秒 |
| heap ≥512MiB，且系统内存充足 | 96～128 / 192MiB | 128 / 192～256MiB | 默认 0；按需最多 64MiB | 15MiB | 0→1；极佳网络可 2 |
| `lowMemory=true` 或 `availMem≤threshold` | 立即降至最低安全层 | 32MiB | 0 | 4MiB | 立即停止 |

只有同时满足以下条件时才考虑 EXO/MPV 256MiB 上限：

- Java heap 至少 768MiB，或 MPV 所在进程系统余量明确充足。
- `availMem` 明显高于 `1.5×threshold`，建议至少 2GiB。
- 当前没有 trim、lowMemory 和中度以上 thermal。
- 资源真实码率证明 128/192MiB 无法达到需要的目标缓冲时间。

### 6.2 系统压力触发条件

| 触发 | 立即动作 |
|---|---|
| `lowMemory=true` 或 `availMem≤threshold` | 停止预载、back=0、禁止升档、缓存降到最低层 |
| `availMem≤1.5×threshold` | 不扩张缓存、不启用 2 线程预载、不升清晰度 |
| `TRIM_MEMORY_RUNNING_LOW` 及更严重级别 | 取消预载、清理可回收缓存、回看缓存归零 |
| thermal=MODERATE | 禁止升档、禁止 2 线程预载和自动插帧 |
| thermal=SEVERE 及以上 | 停止预载，软解/高分辨率降一级，优先低功耗硬解/直出 |

## 七、按资源场景的建议值

| 场景 | 前向缓存目标：初始→上限 | 起播 / 重缓冲 | 码率与预载策略 |
|---|---|---|---|
| 本地文件 | 1→15 秒 | 0.5～1 / 1 秒 | 不做网络预载，back 默认 0 |
| 稳定 LAN | 5→30 秒 | 1 / 1～2 秒 | 1 线程即可；吞吐明显充足再扩张 |
| 网盘 progressive Range | 20～30→60 秒 | 1.5～3 / 3 秒，失败后 5、8 秒 | ratio≥1.4 且稳定后才预载 |
| HLS/DASH 点播 | 30→50 秒 | 1 / 2～3 秒 | 最高轨码率≤0.7×可信吞吐 |
| 普通稳定直播 | 10～20→30 秒 | 1～2 / 2～3 秒 | ABR 安全系数 0.6～0.7，不预载，不保留 back |
| 低延迟直播 | 3～8→10 秒 | 0.5～1 / 1 秒 | 不预载、不保留 back，按 live offset 限制 |
| 外部 loopback | 30→60 秒 | 3 / 5 秒 | 不信任本地腿吞吐；默认不预载 |
| 软件解码 | 15→30 秒 | 1～2 / 2～3 秒 | low-RAM 从 720p30/3Mbps 起；普通设备最多先试 1080p30/6Mbps |
| 4K/HDR 硬解 | 20～30→45～60 秒 | 2 / 3～5 秒 | 按真实 codec、当前输出模式和内存计算；ratio≥1.5 才预载 |
| 经常向后 Seek | 前向不变 | 不变 | back 开 15 秒/16～32MiB；高内存最多 30 秒/64MiB |

### 7.1 回看缓存自动策略

- 默认 back buffer 为 0，符合 Media3 官方默认，也避免 MPV 默认持有大量历史包。
- 10 分钟内检测到至少 2 次明显向后 Seek 后，开启 15 秒或 16～32MiB。
- 高内存设备且持续频繁回看时，最多增加到 30 秒或 64MiB。
- 10 分钟没有向后 Seek、发生 trim/lowMemory、进入直播或外部不可 Seek 资源时立即归零。

### 7.2 预载自动策略

建议沿用并扩展现有 EXO 状态机：

- ratio `<1.15`：暂停预载。
- 恢复要求 ratio `≥1.40`、前台缓冲达到安全线，并持续稳定 10～15 秒。
- 1 线程普通预载：10～20 秒。
- 2 线程快速预载：ratio `≥3.0`、buffer `≥20 秒`、稳定 `≥30 秒`，只允许直连或 App 可控服务。
- 重缓冲、Seek、underrun、lowMemory、trim 或 thermal≥MODERATE 时立即取消。
- 外部 loopback 默认 0；只有代理能提供真实上游状态且前台缓冲≥40秒时才允许 1 线程。

## 八、运行时触发阈值和防抖

### 8.1 清晰度/码率降级

满足任一条件：

- 发生重缓冲：立即降一级或限制码率。
- 可信吞吐/媒体码率 `<1.0` 持续 3～5 秒。
- ratio `<0.85`：无需等待，立即降级。
- time-to-empty 进入 30 秒以内并持续下降。
- 10 秒窗口掉帧超过约 5%，或持续每秒 4 帧以上。
- thermal=SEVERE、decoder 错误或软解长期超载。

### 8.2 清晰度/码率升级

同时满足：

- ratio `≥1.4`。
- 前向缓冲 `≥20 秒`。
- 最近 20～30 秒无重缓冲、无明显负斜率、无严重掉帧。
- 当前内存高于安全线，thermal 不高于 LIGHT。
- 当前显示模式和真实 decoder 能力支持目标轨道。

升级后至少 30～60 秒内不得再次升级；降级可以快速发生。

### 8.3 重缓冲阈值

建议初始值：

- 本地/LAN：1 秒。
- HLS/DASH：2 秒。
- 普通远程 VOD：3 秒。
- 外部 loopback/波动网盘：3～5 秒。

自学习级别建议保留 `2/3/5/8/15 秒`，但：

- 15 秒只用于多次严重重缓冲、没有可降轨的单码率资源。
- 学习结果必须按“网络类型＋播放路径＋协议＋资源类型”隔离。
- 应设置过期时间，避免一次糟糕会话永久影响其他资源。
- 干净会话连续 2 次后逐级降低的现有思想可以保留。

### 8.4 EXO 网络保护降速

播放速度降到 0.97～1.00 可以作为最后一道轻度保护。自动降到 0.85 会明显改变片长：两小时影片约增加 21 分钟，不属于通用播放器的标准缓存策略。

建议：

- 自动轻度保护：0.995～0.985。
- 自动最低值：0.97。
- 低于 0.97：只在单码率、无可降轨、即将耗尽缓冲且用户明确允许时启用。
- 有多码率轨道时优先降轨，不能用降速替代 ABR。

## 九、实施优先级

### P0：先修正确性问题

1. 取消 HLS 代理无条件删除低 variant，保留完整 master playlist。
2. 修正 EXO `capByBandwidth()`，把安全码率真正写入 `maxVideoBitrate`。
3. 移除 EXO 20～40Mbps 乐观初值，恢复 Media3 内置初始估计。
4. 流媒体与本地播放使用独立 LoadControl 参数；流媒体默认 `prioritizeTime=false`。

### P1：建立共享自动环境层

实现统一 `PlaybackEnvironment`/`PlaybackAutoContext`，向三个内核提供：

- Java heap、system memory、PSS/native、trim、thermal。
- 当前显示模式、真实轨道和 codec 能力。
- 资源/协议/live/Range/播放路径分类。
- 可信吞吐、buffer slope、time-to-empty、重缓冲、掉帧和 Seek 行为。

该层只提供事实和统一分级，内核策略仍分别实现，避免把 EXO、MPV、IJK 不同语义强行映射为同一参数。

### P1：完善 EXO 自动

- 修复带宽 cap 和真实 codec 能力。
- 本地/流媒体 LoadControl 分离。
- target bytes 同时受当前 Java 使用量和系统压力约束。
- 重缓冲学习按上下文隔离并过期。
- `onTrimMemory`、lowMemory、thermal 能实时停止预载和缩容。

### P1：实现 MPV 自动缓存控制器

- 初始按内存分级选择 32/64/128MiB。
- 使用 `raw-input-rate`、cache duration、forward bytes、underrun 和媒体码率动态扩张到 48/128/192/256MiB。
- back 默认 0，根据向后 Seek 行为开启。
- 重缓冲等待从 2 秒起，根据当前会话逐级变为 3/5/8 秒。
- HLS 根据可信吞吐选择初始 variant；发生持续 underrun 时允许重新选择并安全重启。
- 预载必须支持前台优先和立即取消。

### P2：实现 IJK 场景和反馈控制

- 解析 HLS/DASH 清单识别真实 live/VOD。
- low-RAM 使用 4～8MiB，普通 VOD 使用 8～15MiB。
- 直播低延迟使用 100/300/1000ms 水位；稳定直播可使用 500/2000/5000ms。
- picture queue 默认保持 3，高分辨率不应盲目增加到 5/8。
- 记录重缓冲和掉帧，按真实结果调整 frame drop、probe 和软解降负载。
- 增加 IJK 硬解失败后的可控软解/其他内核回退。

### P3：逐步移除固定档位

建议顺序：

1. 自动档覆盖并验证推荐/均衡的成功场景。
2. 将“均衡”合并到“自动”，先保留兼容、轻量和自定义作为故障逃生通道。
3. 当自动档在低内存、普通电视、高内存电视、直播、网盘 Range、外部 loopback、软解和 4K/HDR 场景完成数据验收后，再评估移除轻量。
4. 兼容档最后移除，因为它承载厂商 codec、输出和协议异常时的固定回退价值。

## 十、验收标准

自动档成熟不应只看某一部影片是否流畅，至少需要覆盖：

| 场景 | 必测指标 |
|---|---|
| low-RAM 设备 | 无 OOM、无系统杀进程、trim 后能缩容 |
| 普通 1080p TV | 起播、重缓冲、内存、掉帧不劣于原版默认 |
| 4K/HDR TV | 真实 codec/显示模式判断正确，缓存不突破安全上限 |
| HLS/DASH 多码率 | 弱网能降轨，网络恢复后有防抖升级 |
| 网盘单码率 Range | buffer slope 和重缓冲控制有效，不依赖不存在的 ABR |
| 外部 loopback | 不误用本地腿吞吐，不让预载争抢前台连接 |
| 普通/低延迟直播 | 正确识别 live，延迟与稳定策略不同 |
| 软件解码 | 真实掉帧/热压力能触发降分辨率或降负载 |
| 高频 Seek | back buffer 按行为开启，内存压力时自动关闭 |
| MPV/IJK HLS | 8/15Mbps/min 选择真实生效，不再被代理强制最高档 |

建议记录以下统一指标：

- 首帧时间。
- 5/30/120 秒 forward buffer。
- p20/p50 下载吞吐。
- 媒体码率和吞吐/码率比。
- 重缓冲次数、总时长和最长单次时长。
- 掉帧总数和每秒掉帧率。
- Java heap、native heap、PSS、系统 avail/threshold。
- thermal 状态。
- 实际 decoder、hwdec、VO/output 和显示模式。
- 预载线程、预载流量、取消原因。
- 自动决策原因、前值、目标值和防抖状态。

只有当自动档在上述矩阵中稳定优于或至少不劣于固定档位，才适合继续移除其他档位。
